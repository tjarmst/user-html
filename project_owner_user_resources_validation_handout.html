How the Project Owner Should Use the /user Resources

1. Start with TRAINING_RESOURCE_INDEX.md

This should be the Project Owner’s first stop.

Purpose

> Which resource do I use, for which audience, and in what order?

The Project Owner should use it to decide:

  • what management needs to read
  • what ordinary staff can reasonably test
  • what trained governance users must learn
  • what requires fixture-based validation
  • which page guide applies to the current question

For the current validation problem, the most important rule from this resource is:

> Do not ask a user to test a workflow whose prerequisites they have not been trained to recognize.

That rule directly applies to:

  • scenario trigger states
  • predecessor selection
  • carry-forward
  • continuity correction
  • threshold-version testing

2. Use PROJECT_OWNER_ORIENTATION_AND_TESTING_BOUNDARIES.md to Answer Management

This is the management-facing defence of the system.

The Project Owner should use it to say:

> Staff difficulty testing the system is real, but it does not prove that the system is defective. It proves that advanced workflows need role-based testing and prepared examples.

This resource should help the Project Owner distinguish four testing roles.

RoleWhat they should test
Ordinary staffReadability, navigation, obvious labels, visible selected item
Trained governance userRecommendation, KPI, pilot, lineage, evidence, learning workflows
Project OwnerWhether the workflow supports the intended governance model
Developer / fixture testerRare branches, scenario trigger states, predecessor/carry-forward logic

This is the most important management message:

> Ordinary staff should not be asked to discover scenario trigger states by trial and error.

3. Use GOVERNANCE_ACTION_CONCEPT_PRIMER.md Before Touching Complex Pages

This is the vocabulary bridge.

The Project Owner should use it before attempting to understand:

  • recommendation series
  • predecessor recommendation
  • carry-forward
  • evidence relinking
  • structural decision conversion
  • scenario pressure
  • learning state
  • lineage drop-off
  • threshold rules

For the current validation problem, the primer should be used to clarify:

A fixture is not a user-discovered state.
A fixture is a prepared data condition with an expected result.

That distinction is essential.

Without it, the Project Owner is still being asked to behave like a developer.

4. Use TRAINING_MANUAL.md as the Operating Map, Not as the Detailed Instruction Book

The Training Manual should now be used to understand the whole operating loop:

diagnose → recommend → decide → execute → measure → review → learn

For fixture validation, the Project Owner should use the manual to ask:

  • Which part of the loop is being tested?
  • What page owns that part?
  • What upstream data must already exist?
  • What role should test it?
  • Is the expected state visible?
  • If the expected state is not visible, is it a defect or simply missing fixture data?

The Training Manual helps the Project Owner avoid the wrong conclusion:

> I cannot find the state, so the UI is broken.

The better conclusion may be:

> The fixture does not exist yet, so this branch is not exercised.

5. Use Page Guides Only After the Concept Is Known

The page guides should be used when the Project Owner has a specific page or test path.

The Project Owner should not start by clicking through the app. The Project Owner should first define:

  • the required state
  • the expected evidence condition
  • the expected UI result

5A. Use Metric Resources Before Validating Score-Heavy Pages

Before validating Diagnostic Input, Score Dashboard, Score Component Details, Alignment Dashboard, KPI Dashboard, Lineage View, Governance Summary, or exports, the Project Owner should read:

  • user/metrics/Metrics explained.md
  • user/metrics/Metric Definitions.md
  • user/metrics/Comprehensive Metric Reference.md
  • user/metrics/Diagnostic Input Data Collection and Scoring.md
  • user/metrics/Score Component Details Page User Guide.md

Validation question:

> Can the tester distinguish Stage A diagnosis, Stage B execution evidence, and Bridge / governance interpretation?

If not, the test should be limited to readability and navigation rather than interpretation accuracy.

  • the role allowed to test it
  • the fixture data required

Carry-Forward / Predecessor Testing

Use:

RECOMMENDATIONS_PAGE_LEARNING_RESOURCE.md
GOVERNANCE_ACTION_CONCEPT_PRIMER.md
TRAINING_MANUAL.md

The Project Owner should define the fixture before testing.

A valid carry-forward / predecessor fixture requires:

Prior-cycle recommendation exists.
Current-cycle recommendation exists.
Both represent the same continuing issue.
A recommendation series exists.
The prior recommendation is eligible as predecessor.
Expected result: predecessor appears.

If those conditions are not known, the test should be recorded as:

Not exercised — fixture not available.

What Is Still Missing for the Project Owner

The learning resources now explain the system, but the Project Owner still needs a fixture-validation guide.

That guide should not be long. It should be a practical bridge from training to testing.

It should answer:

  • What branch are we trying to validate?
  • What data must exist before the UI can show it?
  • Which page should show it?
  • What result do we expect?
  • Who is qualified to test it?
  • What do we record if the data is missing?

Without this, the Project Owner still has to translate complex concepts into test cases manually.

That is the remaining cognitive-load problem.
