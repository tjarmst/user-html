Recommendations Page Operating Guide

Workplace Conditions Governance

Fiftysixth_pass Stage 6C.4 rewrite

Purpose of this guide

This guide explains how to use the Recommendations page after the Governance Action Pages refactor.

The page is no longer best understood as a long set of recommendation cards where every control appears in a single vertical stream. It is now a selected-workspace page.

The user first selects one recommendation from a worklist. The page then shows the selected recommendation and lets the user choose the relevant workspace area:

  • Overview
  • Evidence
  • Workflow
  • Continuity
  • Learning
  • Convert

This guide is written for trained governance users, Project Owners, and implementation leads. It also helps management understand why ordinary staff should not be asked to test every advanced action path without training or prepared data.

The Recommendations page sits inside the system operating loop:

> diagnose -> recommend -> decide -> execute -> measure -> review -> learn

A recommendation is the bridge between diagnosis and governed action. It is not proof that action has worked. It is a structured claim that governance can accept, defer, test, convert, link to evidence, carry forward, or close.

In metric terms, Recommendations translates Stage A diagnosis into candidate Stage B action. A recommendation can be triggered by structural health, symbolic legitimacy, integrity gap, change readiness, burnout risk, trust, AI capture risk, contradiction count, or execution feedback. It remains a governed prompt until downstream decision, pilot, KPI, evidence, and learning signals support it.

For the metric framing behind recommendations, use user/metrics/Metrics explained.md and user/metrics/Comprehensive Metric Reference.md.

Before using this guide

Users should first read:

  1. PROJECT_OWNER_ORIENTATION_AND_TESTING_BOUNDARIES.md
  2. GOVERNANCE_ACTION_CONCEPT_PRIMER.md

Those two documents explain why the system requires training, why management's concern about complexity is valid, and which users should test which parts of the system.

This page guide assumes the user already understands these basic terms:

  • assessment cycle
  • recommendation
  • evidence note
  • workflow status
  • learning state
  • structural decision
  • conversion
  • recommendation series
  • predecessor recommendation
  • carry-forward
  • continuity correction

What the Recommendations page is for

Use the Recommendations page to:

  • generate or refresh recommendations for the selected assessment cycle;
  • inspect active recommendations for that cycle;
  • review rationale, priority, domain, evidence count, decision count, owner, due date, learning state, and continuity state;
  • link existing evidence notes to a recommendation;
  • update workflow status, owner, and due date;
  • connect recommendations across assessment cycles through recommendation series;
  • record learning actions after monitoring, testing, validating, contradicting, or superseding a recommendation;
  • create or link a structural decision from the selected recommendation;
  • preserve review history and audit traceability.

The page is for governance work. It is not merely a task list and not merely an HR recommendation list.

What the page is not for

The Recommendations page is not for:

  • casual staff testing of every advanced workflow;
  • proving cross-cycle predecessor logic without prepared data;
  • changing KPI threshold rules;
  • editing pilots or pilot metrics;
  • performing full lineage diagnosis;
  • replacing governance judgment with automatic system output;
  • treating a generated recommendation as proof that the proposed action is correct.

A recommendation should be treated as a governance proposal. It becomes stronger only when evidence, decisions, execution, KPIs, review, and learning support it.

The page pattern

The current page follows this pattern:

  1. Readiness panel
  2. Recommendation lifecycle summary
  3. Audit-visible retired recommendations, where present
  4. Recommendation worklist
  5. Selected recommendation header
  6. Workspace selector
  7. Workspace-specific content and actions

This pattern means users should not expect every action to be visible at once.

The safe sequence is:

  1. Confirm the current organization and assessment cycle.
  2. Review whether there are live/current recommendations.
  3. Use the worklist to choose one recommendation.
  4. Confirm the selected recommendation header.
  5. Choose the workspace area that matches the task.
  6. Read the local context before using any write action.

Readiness and empty states

At the top of the page, the readiness panel checks whether the required workspace context exists.

If no organization or assessment cycle is selected, the page should not proceed into recommendation actions.

If the selected cycle has no recommendations, the page may explain that no repository-backed recommendations are attached to the cycle yet. Depending on the scorecard state, it may show potential recommendations that can be generated from the current scorecard.

A blank or limited page is not automatically a defect. Ask:

  • Is an organization selected?
  • Is an assessment cycle selected?
  • Has a scorecard been generated for the cycle?
  • Did recommendation rules trigger recommendations?
  • Were recommendations retired by regeneration?
  • Does this cycle need recommendations to be generated or carried forward?

Lifecycle summary and retired recommendations

The page shows lifecycle metrics such as:

  • Live/current
  • Retired by regeneration
  • Preserved/updated
  • Reactivated

These metrics help the user distinguish active work from audit history.

Live/current recommendations

Live/current recommendations are the recommendations the user can actively work with in the selected cycle.

Retired by regeneration

Retired-by-regeneration records preserve audit history when recommendation regeneration replaced or retired a previous recommendation. They are not ordinary current work items.

Do not treat a retired audit row as a recommendation that should be edited in the normal workflow. Its purpose is traceability.

Recommendation worklist

The worklist is the user's entry point into the page.

It summarizes recommendations so users can choose one item for detailed work. Typical fields include:

  • recommendation title;
  • domain;
  • priority;
  • workflow status;
  • owner;
  • due date;
  • learning state;
  • continuity status;
  • linked evidence count;
  • linked decision count;
  • escalation or scenario state;
  • rationale snippet;
  • cycle label.

Use the worklist to decide which recommendation needs attention first.

The worklist is for triage and selection. It is not the place where most advanced actions are performed.

Selected recommendation header

After the user selects a recommendation, the page shows a selected recommendation header.

Before taking action, confirm:

  • recommendation title;
  • priority;
  • workflow status;
  • continuity state;
  • owner;
  • due date;
  • evidence count;
  • linked decision count;
  • cycle;
  • domain;
  • category;
  • learning state.

This header is the anchor for all workspace actions. If the user cannot tell which recommendation is selected, they should not use action controls.

Workspace selector

The Recommendations page has six workspace areas:

WorkspaceMain questionTypical action
OverviewWhy does this recommendation exist?Inspect rationale and linked decision context.
EvidenceWhat evidence is linked or should be linked?Relink existing evidence.
WorkflowHow is governance handling this recommendation operationally?Update status, owner, and due date.
ContinuityHow does this recommendation relate to earlier or later cycles?Create/link/update series and predecessor context.
LearningWhat has been learned from action, testing, or review?Apply learning action and review learning history.
ConvertShould this recommendation become a formal structural decision?Create/link structural decision and evidence.

Users should choose the workspace that matches the task. They should not try to infer every hidden data-flow rule from the page alone.

Workspace guide

1. Overview

Purpose

Use Overview to understand why the selected recommendation exists.

The area may show:

  • rationale;
  • escalation state;
  • scenario state;
  • structural health, symbolic legitimacy, and integrity-gap values where available;
  • mitigation-aware domain state;
  • linked structural decisions, if any.

How to use it

Ask:

  • What problem or governance condition is this recommendation responding to?
  • Is the recommendation based on scorecard conditions, evidence, mitigation state, scenario pressure, or a combination?
  • Is this a strong action candidate, a monitoring candidate, or a recommendation needing more evidence?
  • Does it already have linked structural decisions?

User caution

The rationale is not proof. It is the recommendation's testable logic. Later evidence, decisions, pilots, KPIs, and learning review may support, qualify, contradict, or supersede it.

2. Evidence

Purpose

Use Evidence to inspect evidence already linked to the selected recommendation and, where appropriate, relink an existing evidence note.

The area may show:

  • linked evidence notes;
  • evidence role;
  • confidence level;
  • evidence narrative snippet;
  • selector for existing evidence notes;
  • action to apply recommendation evidence relink.

What evidence relinking means

Evidence relinking attaches an existing evidence note to the selected recommendation. It does not create a new evidence note. It changes the recommendation's evidence traceability.

This matters because later review surfaces may use linked evidence to qualify recommendation confidence, conversion, decision rationale, governance review, and board-pack interpretation.

Before relinking evidence

Confirm:

  • the selected recommendation is correct;
  • the evidence note genuinely supports, explains, qualifies, or contradicts this recommendation;
  • the evidence is not being attached merely because it sounds related;
  • a later reviewer would understand why the evidence was linked.

Safe-use rule

Relink evidence only when the evidence relationship is clear. If the relationship is uncertain, add or revise an evidence note first rather than forcing a linkage.

3. Workflow

Purpose

Use Workflow to update the operational handling of the selected recommendation.

The area may include:

  • status selector;
  • owner selector;
  • due date field;
  • Save Recommendation button.

Workflow status is not learning proof

Workflow status records governance handling. It does not prove that the recommendation worked.

For example:

  • accepted means governance accepts that the recommendation should be pursued or considered.
  • implemented means action may have occurred.
  • Neither status proves that conditions improved.

Learning state and evidence are needed to judge whether the recommendation has been validated, contradicted, superseded, or reopened.

Before saving workflow changes

Confirm:

  • selected recommendation;
  • current status;
  • new status;
  • owner;
  • due date;
  • whether the status change will make the recommendation appear more mature than the evidence supports.

Safe-use rule

Do not use workflow status to create an appearance of progress. Use it to record actual governance handling.

4. Continuity

Purpose

Use Continuity to connect the selected recommendation to its cross-cycle history.

Continuity helps governance answer:

  • Is this recommendation new?
  • Is it carried forward from a prior cycle?
  • Is it a revision of an earlier recommendation?
  • Is it split from or merged from prior work?
  • Has it been superseded, contradicted, validated, or closed?

Why continuity is difficult

Continuity depends on assessment cycles, recommendation series, predecessor recommendations, and data eligibility. An ordinary user may not be able to validate these relationships by exploration.

This is expected. Continuity is an advanced governance function.

Recommendation series

A recommendation series is a cross-cycle thread linking related recommendations over time.

Create a new series when this is the first occurrence of the issue.

Link to an existing series when the selected recommendation continues, revises, splits, merges, or closes an existing thread.

Predecessor recommendation

A predecessor is the earlier-cycle recommendation that the current recommendation follows from.

A predecessor can only be selected if eligible prior-cycle recommendation data exists. If no predecessor appears, that does not automatically mean the UI is broken.

Continuity actions

Depending on current state, the area may allow:

  • create a new series and link the recommendation;
  • link the recommendation to an existing series;
  • update a continuity link;
  • select or change predecessor recommendation;
  • add change summary;
  • add continuity rationale;
  • use bounded continuity correction controls;
  • remove a series link.

Warning before action

The page now warns that continuity actions change cross-cycle lineage and governance interpretation.

Take that warning seriously. Continuity is not just a label. It affects how future review understands whether the organization is learning, repeating, fragmenting, validating, contradicting, or closing issues across cycles.

Before saving continuity changes

Confirm:

  • selected recommendation;
  • current cycle;
  • selected series;
  • continuity status;
  • predecessor recommendation, if required;
  • change summary;
  • continuity rationale;
  • whether the relationship is genuinely historical and not merely similar wording.

When to use continuity correction

Use continuity correction only when an existing link is wrong. Examples:

  • wrong predecessor;
  • wrong series;
  • recommendation should be detached from a series;
  • predecessor should be removed.

Continuity correction is not ordinary page use. It is trained governance-administrator or Project Owner work.

Smoke-test boundary

Do not ask ordinary staff to prove predecessor/carry-forward behavior by exploration. Use prepared fixture data if this needs to be tested.

5. Learning

Purpose

Use Learning to record what has been learned about the selected recommendation after action, testing, monitoring, or review.

The area may show:

  • selected recommendation context;
  • current learning state;
  • current learning note;
  • learning action selector;
  • learning note field;
  • recommendation learning/workflow history.

Learning state is different from workflow status

Workflow status asks:

> What is governance doing with this recommendation?

Learning state asks:

> What has evidence and implementation experience shown about this recommendation?

A recommendation can be accepted but untested. It can be implemented but contradicted. It can be deferred but still important. It can be closed because it was superseded by a better formulation.

Learning action options

The current UI may include actions such as:

  • Mark in test
  • Mark validated
  • Mark contradicted / reopen
  • Mark superseded

These actions correspond to service-level learning transitions. The exact internal action names are less important than the governance meaning.

Before applying a learning action

Confirm:

  • selected recommendation;
  • current learning state;
  • evidence or implementation experience supporting the new state;
  • whether the change should also affect workflow, continuity, decision status, pilot status, or governance review;
  • whether the learning note explains the reason clearly enough for later review.

Safe-use rule

Do not mark a recommendation validated simply because work has started. Validation requires evidence that the expected effect is supported.

Do not mark contradicted simply because implementation is hard. Contradiction means evidence conflicts with the expected claim or mechanism.

6. Convert

Purpose

Use Convert when the selected recommendation should become, or be linked to, a formal structural decision.

A structural decision is a governed choice about an organizational structure, mechanism, practice, role, pathway, accountability arrangement, or operating condition.

Conversion moves the recommendation from advisory direction toward formal governance action.

What the Convert area shows

The Convert area now provides a context panel before conversion controls. It should show:

  • selected recommendation;
  • domain;
  • current status;
  • linked structural decision state, if any;
  • explanation that conversion creates or links a structural decision from the selected recommendation.

It may also allow the user to choose an evidence note to link on conversion.

Before converting

Confirm:

  • selected recommendation;
  • whether governance is ready to make a structural decision;
  • whether the recommendation has enough evidence or rationale for formal decision-making;
  • whether a linked structural decision already exists;
  • whether the selected evidence note is the right support for conversion;
  • whether conversion is premature.

Safe-use rule

Do not convert every recommendation. Convert when the organization is ready to make a governed structural choice or create a formal decision record.

Common user scenarios

Scenario A — No recommendations appear

Possible explanations:

  • no active assessment cycle;
  • no scorecard for the cycle;
  • no recommendation rules triggered;
  • recommendations have not been generated;
  • live recommendations were retired by regeneration;
  • the selected cycle is not the cycle you expected.

What to do:

  1. Confirm organization and assessment cycle.
  2. Confirm scorecard exists.
  3. Read any page message about generated preview recommendations.
  4. Use Generate / refresh only when appropriate.

Scenario B — A recommendation has no linked evidence

This is not automatically a defect.

Ask:

  • Is there an existing evidence note that should be linked?
  • Is the recommendation still only a score-triggered proposal?
  • Should evidence be created first on the Evidence Notes page?

Scenario C — No predecessor recommendation is available

This is not automatically a defect.

A predecessor requires valid prior-cycle recommendation data. The selected series and selected recommendation must make historical sense together.

If no valid predecessor exists in the current data, record the path as not exercised, not failed.

Scenario D — Convert appears unavailable or sparse

The current Stage 6B patch added selected recommendation and conversion context before conversion controls. If that context is not visible, treat it as a defect.

If context is visible but conversion does not proceed, check whether evidence, decision, or selected-cycle prerequisites exist.

Scenario E — Learning history is present but confusing

Learning/workflow history may include status updates, regeneration events, preserved identity events, or learning actions.

Read the history as audit traceability, not as a simple user-friendly story. If management needs a clearer story, use governance review and summary pages rather than expecting this area to be a complete narrative.

Role-based testing boundaries

Ordinary staff can test

Ordinary staff can reasonably test whether:

  • the page purpose is understandable;
  • the selected recommendation is visible;
  • workspace labels make sense;
  • obvious empty states are understandable;
  • they can tell which areas are for trained governance users;
  • basic inspection is possible without changing data.

Ordinary staff should not be asked to validate:

  • predecessor eligibility;
  • continuity correction;
  • carry-forward logic;
  • conversion integrity;
  • evidence-linking correctness;
  • regeneration identity preservation;
  • scenario-trigger consequences.

Trained governance users can test

Trained governance users can test:

  • evidence relinking;
  • workflow status update;
  • ordinary continuity linking when valid data exists;
  • learning action updates;
  • conversion to structural decision;
  • interpretation of lifecycle and worklist fields.

Project Owner or implementation lead can test

The Project Owner can test:

  • whether the page supports the operating loop;
  • whether action contexts are visible before write controls;
  • whether management can understand why training is required;
  • whether user roles are clearly bounded;
  • whether a future page guide or smoke script is needed.

Developer or fixture-based validation should test

Developer or fixture validation should test:

  • predecessor/carry-forward eligibility;
  • continuity correction edge cases;
  • regeneration preserve/update/reactivate behavior;
  • conversion persistence edge cases;
  • evidence-link integrity;
  • cross-cycle series timeline correctness.

Governance interpretation rules

Recommendations are not proof

A recommendation is a structured governance claim. It still needs evidence, decision, execution, measurement, review, and learning.

Evidence is not decoration

Evidence linkage changes what later review can see and rely on.

Workflow is not learning

A recommendation can be accepted or implemented without being validated.

Continuity is not a filing label

Continuity determines how cross-cycle learning is interpreted.

Conversion is a governance action

Converting a recommendation creates or links a structural decision. It should not be treated as a convenience button.

Learning state is a claim about evidence

Learning state should reflect what has actually been learned, not what the user hopes will be true.

Recommended operating sequence for trained users

  1. Confirm the organization and assessment cycle.
  2. Review lifecycle summary.
  3. Scan the recommendation worklist.
  4. Select one recommendation.
  5. Read the selected recommendation header.
  6. Open Overview to understand rationale and context.
  7. Open Evidence to inspect or relink evidence.
  8. Open Workflow only when operational handling should be updated.
  9. Open Continuity only when cross-cycle linkage is being reviewed or maintained.
  10. Open Learning only when evidence or implementation experience supports a learning-state update.
  11. Open Convert only when governance is ready to create or link a structural decision.
  12. Record notes and rationale clearly enough for later review.

Quick checklist before pressing a write-action button

Before using any save, apply, link, convert, or correction button, ask:

  • What recommendation is selected?
  • What workspace am I in?
  • What will this action change?
  • Is the required evidence or prerequisite data present?
  • Would a later reviewer understand why this action was taken?
  • Is this action appropriate for my role?

If any answer is unclear, stop and seek clarification.

Management-facing summary

The Recommendations page is powerful because it preserves the path from diagnosis to recommendation, evidence, decision, execution, review, and learning. That same power makes the page unsuitable for untrained exploratory testing of every feature.

Management should not conclude that the system lacks value because staff cannot intuit every continuity or conversion rule. The correct conclusion is that the system requires:

  • concept training;
  • role-specific operating guides;
  • prepared smoke-test scripts;
  • fixture-based validation for advanced cross-cycle behavior;
  • clear distinction between ordinary staff inspection and trained governance action.

The page is fit for trained governance use when users understand the selected-workspace model and the consequences of evidence, workflow, continuity, learning, and conversion actions.
