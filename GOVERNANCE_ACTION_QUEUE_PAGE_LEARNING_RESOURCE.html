Governance Action Queue Page Learning Resource

This guide teaches users how the **Governance Action Queue** page is now organized around queue posture, selected-action inspection, ownership management, and closure handling.

The page asks a practical governance question:

> Which review findings have become ownerable governance work, and what is their current ownership, progress, and resolution state?

The queue is for accountable follow-up work. It is not a list of every visible warning.

Purpose

Use Governance Action Queue to answer four queue-management questions:

  • **Review Queue Posture:** What actions are currently queued, and what do their routing, context, and board-attention signals show?
  • **Inspect Selected Action:** What does one queued action mean before changing ownership or resolution state?
  • **Manage Ownership and Progress:** Who owns the action, when is it due, and what workflow status should it have?
  • **Resolve and Close Action:** What closure outcome applies, and what resolution summary explains it?

The page begins with cycle-level metrics before showing the queue-focus controls.

Required Starting Point

The page requires a selected assessment cycle.

If no cycle is selected, the page asks the user to select one first.

The page reads governance action summary rows for the current cycle. It also reads organization users for owner labels and challenge records so challenge-linked actions can display clearer linked-entity context.

Top Summary Metrics

The top of the page shows:

  • open actions
  • overdue actions
  • resolved actions
  • contradicted open actions
  • board attention actions
  • interpretive snapshot caption when available

These metrics describe the queue's current posture. They do not by themselves prove that governance is healthy or unsafe.

An empty queue can be legitimate when there is no ownerable follow-up work. It can also mean upstream review work is incomplete. Treat an empty queue as something to verify, not something to celebrate automatically.

Empty Queue Behavior

If there are no governance action rows, the page shows **Queue posture** directly and does not show the queue-focus selector.

The empty-state message explains that the queue is populated only when learning-driven follow-up work is created, such as contradiction, reopen or revise requests, or generated actions from current learning signals.

The page also reminds users that monitor-only and supportable semantic consequences do not create governance queue items by default.

Queue Focus Buttons

When queue rows exist, the **Queue focus** selector contains:

  • Review Queue Posture
  • Inspect Selected Action
  • Manage Ownership and Progress
  • Resolve and Close Action

Each focus area serves a different task.

Review Queue Posture

Use **Review Queue Posture** when the question is what the queue currently contains.

This area shows the full queue table after display cleanup. Rows can include:

  • action ID
  • title
  • status
  • priority
  • owner
  • due date
  • linked entity type and ID
  • linked challenge label when available
  • handling
  • routing
  • review context
  • interpretive snapshot line
  • resolution summary when present

Use this area before row-level work. It helps users see whether the queue is dominated by overdue work, board-attention items, contradiction-linked work, reassessment items, or closure-ready items.

Inspect Selected Action

Use **Inspect Selected Action** when the user needs to understand one queue item without changing it.

This area shows:

  • **Select governance action** control
  • selected action summary
  • action ID
  • status
  • priority
  • owner
  • title
  • linked entity reference
  • handling
  • routing
  • review context
  • interpretive snapshot line
  • resolution summary if one exists

Use this area before assigning, updating, or resolving an action. The goal is to understand what the action is accountable for and how the system has classified its handling.

Manage Ownership and Progress

Use **Manage Ownership and Progress** when the question is who owns the work and what its workflow state is.

This area shows:

  • **Select governance action** control
  • **Assign owner** selector
  • **Due date** input
  • **Workflow status** selector
  • **Save assignment / status** button
  • **Mark in progress** button

Workflow status options are:

  • open
  • in_progress
  • deferred
  • resolved
  • cancelled

**Save assignment / status** updates the selected action's owner, due date, and workflow status.

**Mark in progress** moves the selected action directly to in-progress with a work-started note.

Use this area to keep ownership and due-date discipline current. Do not use it to explain closure; closure belongs in Resolve and Close Action.

Resolve and Close Action

Use **Resolve and Close Action** when the governance work is ready for a closure outcome.

This area shows:

  • **Select governance action** control
  • selected action summary
  • **Resolution outcome** selector
  • **Resolution summary** text area
  • **Resolve action** button

Resolution outcomes are:

  • confirmed_closed
  • revised_reissued
  • superseded
  • deferred
  • escalated
  • converted_to_pilot
  • converted_to_recommendation
  • no_action_required

The page requires a resolution outcome before resolving. If the user clicks **Resolve action** without choosing an outcome, the page asks them to choose one first.

The resolution summary should explain what happened. It should not merely repeat that the action was closed.

Routing, Context, And Snapshot Cues

Queue rows may show:

  • handling label
  • routing line
  • review context
  • interpretive snapshot line

Use these cues to distinguish:

  • monitor-only visibility
  • caution prompts
  • reassessment work
  • blocked evidence work
  • redesign-required work
  • board-attention work
  • challenge-linked follow-up

Semantic routing guides the queue, but it does not mean every warning becomes an action. Monitor-only and supportable findings should not create queue items by default.

When Work Belongs In The Queue

Queue work is appropriate when the row is both consequential and ownerable.

Look for:

  • reassessment handling where a conclusion, recommendation, decision, pilot, KPI, scenario, or continuity row needs review
  • blocked-pending-stronger-evidence handling where progression should pause until evidence improves
  • redesign-required handling where the current approach appears misaligned or contradicted
  • unresolved or challenged human validation records with follow-up required
  • contradiction or incompleteness that affects a live governance decision
  • weak execution paths where a named owner can strengthen evidence, mitigation, or workflow state
  • scenario pressure where mitigation is unplanned, ownerless, overdue, or contradicted by execution evidence

The practical test is:

> Can a specific person do a specific review, evidence, mitigation, decision, pilot, KPI, or correction task?

If the answer is no, the item may be monitoring context rather than queue work.

When Work Should Not Become Queue Work

Do not create queue work merely because:

  • a warning is visible
  • a board-pack line mentions caution
  • a score moved unfavorably
  • evidence is low confidence but does not imply a concrete follow-up task
  • a recommendation is proposed but has no unresolved challenge or blockage
  • a monitor-only continuity warning is visible
  • the item is supportable under current evidence

These cases may still need visibility, monitoring, evidence collection, or ordinary workflow discipline. They do not automatically need a governance action.

Downstream Impact

Governance Action Queue feeds downstream interpretation by showing whether governance follow-up has ownership, due dates, status, and closure outcomes.

It connects to:

  • Governance Summary, through tasking and resolution discipline
  • Comparative Cycle Review, through governance action movement
  • Review History, through ownership, status, and resolution events
  • board-pack governance tasking sections
  • upstream review pages that generate or justify ownerable work, including Governance Summary, Governance Execution Review, Comparative Cycle Review, Scenario Effectiveness Review, and human validation challenge review

The queue should help users distinguish visible governance concerns from accountable work.

Common Mistakes

Avoid creating queue actions for every warning.

Avoid assuming an empty queue proves the cycle is safe.

Avoid leaving high-priority actions unassigned.

Avoid updating workflow status when the real need is a resolution outcome.

Avoid resolving actions without a meaningful resolution summary.

Avoid treating board attention as the same as ownership.

Avoid using vague action titles or summaries when the action should name the specific claim, evidence gap, mitigation, decision, pilot, KPI, challenge, or continuity issue.

Avoid creating duplicate follow-up when an existing action already covers the issue. Update the existing action instead.

Best-Practice Review Pattern

  1. Select the intended assessment cycle.
  2. Read the top summary metrics and snapshot caption.
  3. If the queue is empty, verify upstream review pages before assuming no work is needed.
  4. Open **Review Queue Posture** to scan all active rows.
  5. Open **Inspect Selected Action** to understand a row before changing it.
  6. Open **Manage Ownership and Progress** to assign owner, due date, and workflow status.
  7. Use **Mark in progress** only when work has actually started.
  8. Open **Resolve and Close Action** when a closure outcome is ready.
  9. Choose the resolution outcome and write a resolution summary that explains what changed.

Training Prompt

If the queue has actions, ask the trainee to select one governance action, inspect its handling, routing, review context, owner, status, and due date, then decide whether to assign it, mark it in progress, defer it, cancel it, or resolve it with a specific outcome.

If the queue is empty, ask the trainee to inspect Governance Summary, Comparative Cycle Review, Governance Execution Review, Scenario Effectiveness Review, and human validation challenge states, then explain why no ownerable follow-up is currently needed.

Completion standard: the user can distinguish visibility from accountable governance tasking and can manage ownership, progress, and closure without over-escalating monitor-only findings.
