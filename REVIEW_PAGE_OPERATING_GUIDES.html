Review-Page Operating Guides

WorkPlace Conditions Governance

Stage 6O

Purpose

This guide helps trained governance users operate the main review pages without directly platform-connected LLM support.

Users may still use normal LLM support services for explanation, summarisation, drafting notes, or help interpreting exported text. However, they should not rely on an LLM to access live application state, infer hidden data, or decide whether a fixture exists.

The user must read what the application actually shows.

---

Who this guide is for

This guide is for trained governance users who already understand the basic operating concepts:

  • recommendation
  • structural decision
  • pilot
  • KPI
  • evidence
  • scenario pressure
  • learning state
  • governance action
  • contradiction / incompleteness
  • weak support
  • supportable under current evidence
  • fixture validation

This guide is not for ordinary staff readability testing.

---

Critical operating rule

> Do not ask users to discover hidden prerequisite states by exploration.

If a page requires a state that is not visible or cannot be named from prepared data, record:

Not exercised — fixture unavailable.

Do not treat missing fixture data as a page defect.

---

Use of normal LLM support

A trained governance user may use normal LLM support to:

  • explain a concept shown on the page;
  • convert page text into a meeting note;
  • summarise exported rows;
  • draft a governance observation;
  • compare a visible result with an expected result;
  • simplify wording for management.

A trained governance user must not use normal LLM support to:

  • claim the LLM has inspected live application state unless the user has pasted/exported it;
  • infer hidden database records that are not shown or exported;
  • decide that a branch passed without a visible row, export, or prepared fixture;
  • replace the application’s actual rendered state with speculation.

Safe LLM prompt pattern:

I am using WorkPlace Conditions Governance. Here is the visible text/export from the page. Please help me classify what is shown, without assuming hidden data.

Review Page 1 — Governance Summary

Page purpose

Governance Summary is the synthesis page. It helps governance users understand overall cycle posture, major concerns, scenario posture, evidence/contradiction posture, and exportable board-pack material.

Use it to answer:

  • What is the current governance picture?
  • What areas require attention?
  • What does the board or governance reviewer need to see?
  • What evidence, contradiction, or scenario posture qualifies the summary?

Before using the page

  1. Confirm the correct organization and assessment cycle are selected.
  2. Click `Refresh Governance Summary` if changes were made elsewhere.
  3. Check the freshness caption.
  4. Do not rely on an old Export tab state after significant changes; refresh first.

Operating areas

AreaUse it for
Decidegovernance decisions, gates, and action posture
Qualifyconfidence, evidence, contradiction, or qualification context
Diagnoseevidence/contradiction/incompleteness posture and diagnostics
Govern Scenariosscenario posture and scenario-related governance attention
Close Learninglearning closure and cycle interpretation
Exportboard-pack / export outputs

Minimum checks

CheckPass / issue / not applicableNotes
Refresh control is visible and used when needed.
The selected cycle/context is clear.
Diagnose shows compact evidence/contradiction/incompleteness posture.
Govern Scenarios shows compact scenario posture.
Detailed tables/charts are still available.
Export renders when needed.
Export delay is expected on first load or after refresh.
Returning to Export without refresh is faster.

What not to infer

Do not infer that every scenario branch has been exercised just because Governance Summary renders correctly.

For scenario trigger validation, use Scenario Effectiveness Review and prepared fixture rules.

Normal LLM support use

You may paste Governance Summary text or export sections into a normal LLM and ask:

Summarise this governance summary for a board reader. Preserve all qualifications and residual risks. Do not remove evidence or contradiction caveats.

Review Page 2 — Comparative Cycle Review

Page purpose

Comparative Cycle Review compares assessment cycles and helps users understand movement, continuity, challenge, and closure.

Use it to answer:

  • What changed between cycles?
  • Which conclusions are stable or contested?
  • Are there unresolved challenges?
  • Are recommendation continuity items visible and reachable?

Before using the page

  1. Confirm the selected cycles.
  2. Click `Refresh Comparative Review` after updates elsewhere.
  3. Confirm selected cycle context remains stable after refresh.

Operating areas

AreaUse it for
Closure Summaryhigh-level closure position and action cues
Close Challengeshuman validation / challenge review
Continuityrecommendation continuity review
Comparative tablescycle-to-cycle movement and interpretation

Minimum checks

CheckPass / issue / not applicableNotes
Refresh control is visible.
Selected cycle context remains stable after refresh.
Closure Summary points to challenge and continuity workflows.
Close Challenges remains reachable.
Continuity remains reachable.
Challenge or continuity absence is understandable as no-data / not applicable.

What not to infer

Do not infer that carry-forward/predecessor validation is complete unless a prepared prior/current recommendation fixture exists.

Normal LLM support use

You may paste cycle comparison text or tables into a normal LLM and ask:

Explain the cycle-to-cycle change shown here. Keep challenge and continuity qualifications visible.

Review Page 3 — Governance Execution Review

Page purpose

Governance Execution Review examines whether governance responses are progressing through execution paths.

Use it to answer:

  • Is the selected recommendation/decision/pilot path healthy?
  • Is there drop-off?
  • Is scenario pressure relevant?
  • Is evidence/KPI context adequate before progression actions?
  • Is learning closure or reopening relevant?

Before using the page

  1. Confirm the selected organization/cycle.
  2. Select the relevant lineage path.
  3. Click `Refresh Governance Execution Review` after updates elsewhere.
  4. Confirm selected cycle/path remains coherent after refresh.

Operating areas

AreaUse it for
Decide Progressiongoverned progression actions and action context
Diagnose Path Healthdrop-off and path diagnostics
Govern Scenario Pressurescenario/mitigation context
Close Learninglearning and reopen candidate context
Inspect Selected Pathworkflow entities, KPI context, and evidence relinking

Minimum checks

CheckPass / issue / not applicableNotes
Refresh control is visible.
Selected path remains coherent after refresh.
Decide Progression shows action context before action controls.
Linked scenario cue is visible or states none.
Linked KPI count is visible or states none.
Evidence gap cue is visible.
Weak execution cue is visible.
Govern Scenario Pressure remains available.
Inspect Selected Path remains available for KPI/evidence context.
Close Learning shows learning/reopen context.

What not to infer

Do not apply a governed action merely because the control is visible. Confirm selected path, scenario pressure, evidence/KPI posture, and learning/path health first.

Normal LLM support use

You may paste the selected-path action context into a normal LLM and ask:

Help me write a short governance note from this selected-path context. Do not infer missing evidence or hidden linked entities.

Review Page 4 — Scenario Effectiveness Review

Page purpose

Scenario Effectiveness Review tests whether scenario pressures are being addressed by evidence-backed execution.

Use it to answer:

  • Which scenario pressures are unsupported?
  • Which are weakly supported?
  • Which may be supportable under current evidence?
  • Where are contradictions or mitigation weaknesses visible?
  • What requires governance attention?

Before using the page

  1. Confirm the selected organization/cycle.
  2. Click `Refresh Scenario Effectiveness Review`.
  3. Start in `Review Scenario Posture`.
  4. Use aggregate posture metrics as orientation, not as proof by themselves.

Operating areas

Minimum checks

CheckPass / issue / not applicableNotes

Linked Entity Evidence remains reachable.
Contradiction and Incompleteness remains reachable.
Governance Attention remains reachable.
Candidate row/entity can be named before classifying a fixture.

Fixture classification reminder

For scenario trigger-state validation, classify each state as:

ClassificationMeaning
PassValid fixture exists and UI/export shows expected state.
Minor issueState is correct but wording/signposting is unclear.
Material defectValid fixture exists but UI/export renders wrong state.
Not exercised — fixture unavailableRequired state is not present in current data.

Do not classify a fixture as Pass from an aggregate count alone. Identify at least one candidate row/entity or export row.

Review Page 5 — Governance Action Queue

Page purpose

Governance Action Queue manages governance actions, ownership, progress, and closure.

Use it to answer:

  • What governance actions exist?
  • Who owns them?
  • What is their status?
  • What selected action is being edited?
  • Is the action ready to close?

Operating areas

AreaUse it for
Review Queue Posturequeue table and posture overview
Inspect Selected Actionselected-action summary and context
Manage Ownership and Progressowner/status/progress updates
Resolve and Close Actionresolution and closure

Minimum checks

CheckPass / issue / not applicableNotes
Queue table/posture appears.
Selected action is visible before inspection.
Inspect Selected Action updates when selection changes.
Manage Ownership and Progress shows selected-action context before controls.
Resolve and Close Action shows selected-action context before closure controls.
Owner/status update is only performed on a safe test row.
Closure is only performed when a safe/valid action is selected.

What not to infer

Do not update ownership, progress, or closure unless the selected-action summary clearly identifies the action being changed.

Normal LLM support use

You may paste a selected-action summary into a normal LLM and ask:

Help me draft a short ownership/progress note for this selected governance action. Do not assume any missing linked entity context.

Review Page 6 — Review History

Page purpose

Review History provides audit/supporting history for governance interpretation.

Use it to answer:

  • What has changed?
  • What was previously accepted, challenged, preserved, retired, or updated?
  • What evidence exists for continuity or lifecycle interpretation?

Minimum checks

CheckPass / issue / not applicableNotes
Review history opens safely.
Events are understandable enough to support audit review.
Event timestamps and event types are visible where available.
Linked entity context is visible where available.
Empty states are understandable.

What not to infer

Do not infer current state from history alone. Use the relevant current page for current status.

Normal LLM support use

You may paste review-history entries into a normal LLM and ask:

Summarise this review history for audit purposes. Keep event types and chronology clear.

Closure rule for Stage 6O

Stage 6O can be closed when:

  • review-page operating guides exist for trained governance users;
  • guides support operation without directly platform-connected LLM access;
  • guides allow normal LLM support for pasted/exported text;
  • guides do not ask users to infer hidden data;
  • guides preserve fixture discipline and residual-risk classification;
  • guides do not reopen design or implementation work.

This document meets those requirements.
