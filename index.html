Training Resource Index and Rollout Sequence

Purpose

This index gives the Project Owner a compact map of the Workplace Conditions Governance training resources after the Stage 6C training-resource update sequence.

Use it to decide:

  • which resource to give to which audience
  • what should be read first
  • what ordinary staff should and should not be asked to test
  • what trained governance users need before using advanced pages
  • what still requires fixture-based validation
  • what remaining older resources may need later review

The central rollout message is:

> The Workplace Conditions Governance platform is a specialist governance-control-room application. It is not a casual self-service dashboard. Training should be role-based, staged, and supported by prepared examples.

Recommended reading order by role

1. Management / sponsor

Management does not need to learn every page.

Recommended reading:

  1. PROJECT_OWNER_ORIENTATION_AND_TESTING_BOUNDARIES.md
  2. Executive extracts from TRAINING_MANUAL.md, especially:
  • Core management message
  • The operating loop
  • User roles and testing boundaries
  • Completion standard for training readiness

Management should understand:

  • why ordinary staff found the system difficult to test
  • why that difficulty does not invalidate the system
  • why advanced testing must be role-specific
  • why prepared fixtures are needed for some validation paths
  • why the product should be positioned as a governance-control-room application, not a casual HR dashboard

Management should not be asked to validate:

  • continuity correction
  • predecessor/carry-forward paths
  • threshold-version effects
  • scenario trigger-state branches
  • lineage edge cases
  • detailed evidence relinking consequences

2. Project Owner / implementation lead

The Project Owner needs the full training architecture.

Recommended reading:

  1. PROJECT_OWNER_ORIENTATION_AND_TESTING_BOUNDARIES.md
  2. GOVERNANCE_ACTION_CONCEPT_PRIMER.md
  3. TRAINING_MANUAL.md
  4. Metric interpretation resources:
  • user/metrics/Metrics explained.md
  • user/metrics/Metric Definitions.md
  • user/metrics/Comprehensive Metric Reference.md
  • user/metrics/Diagnostic Input Data Collection and Scoring.md
  • user/metrics/Score Component Details Page User Guide.md
  1. Page operating guides for any area being validated:
  • RECOMMENDATIONS_PAGE_LEARNING_RESOURCE.md
  • KPI_DASHBOARD_PAGE_LEARNING_RESOURCE.md
  • LINEAGE_VIEW_PAGE_LEARNING_RESOURCE.md
  • PILOT_TRACKER_PAGE_LEARNING_RESOURCE.md

The Project Owner should be able to explain:

  • what the system is for
  • why it is complex
  • how the operating loop works
  • which roles can test which parts
  • when a missing workflow is a valid empty state rather than a defect
  • which checks require prepared fixture data
  • where training materials must be updated before user rollout

3. Ordinary staff / general user reviewer

Ordinary staff should receive a limited orientation.

Recommended reading:

  1. selected extracts from PROJECT_OWNER_ORIENTATION_AND_TESTING_BOUNDARIES.md
  2. selected extracts from TRAINING_MANUAL.md
  3. only the page guide for the specific page they are asked to review

Ordinary staff can reasonably test:

  • page opens
  • page purpose is broadly understandable
  • selected item is visible
  • obvious labels are understandable
  • empty states are not alarming
  • navigation feels coherent after basic orientation

Ordinary staff should not be asked to test:

  • predecessor/carry-forward eligibility
  • continuity series correction
  • recommendation regeneration identity preservation
  • threshold-rule versioning effects
  • scenario trigger branches
  • conversion-to-decision semantics
  • lineage completeness across cycles
  • evidence relinking consequences
  • precise classification or scoring edge cases

If ordinary staff cannot validate those advanced paths, record the result as:

Out of ordinary-staff testing scope.

Do not treat that as a product failure.

4. Trained governance user

Trained governance users need the concept primer and relevant page guides.

Recommended reading:

  1. GOVERNANCE_ACTION_CONCEPT_PRIMER.md
  2. TRAINING_MANUAL.md
  3. the relevant page operating guide

For Recommendations work:

RECOMMENDATIONS_PAGE_LEARNING_RESOURCE.md

For KPI work:

KPI_DASHBOARD_PAGE_LEARNING_RESOURCE.md

For lineage work:

LINEAGE_VIEW_PAGE_LEARNING_RESOURCE.md

For pilot work:

PILOT_TRACKER_PAGE_LEARNING_RESOURCE.md

Trained governance users can test:

  • selected-item context
  • evidence interpretation
  • recommendation workflow updates
  • continuity actions where data is valid
  • conversion to structural decision
  • KPI creation and reassessment
  • evidence relinking
  • pilot metrics and linked KPIs
  • pilot outcome recomputation
  • lineage and drop-off interpretation
  • review-history implications

They should still use prepared examples for advanced branches.

5. Developer / fixture-based validator

Developer or fixture-based validation is required for rare or data-dependent paths.

Needed later if the Project Owner wants formal closure of:

  • scenario trigger-state branches
  • insufficient evidence
  • weakly evidenced / weak support
  • supportable under current evidence
  • predecessor/carry-forward eligibility
  • recommendation series correction states
  • threshold-rule version comparison and reassessment edge cases
  • broken lineage states
  • mixed pilot signal states
  • contradicted evidence states
  • no-data and partial-data combinations

The correct testing form is not ordinary exploratory smoke testing. It is prepared fixture testing with known expected states.

Suggested rollout sequence

Phase 1 — Management alignment

Audience:

  • sponsor
  • management
  • Project Owner
  • implementation lead

Resources:

  • PROJECT_OWNER_ORIENTATION_AND_TESTING_BOUNDARIES.md
  • selected sections of TRAINING_MANUAL.md
  • user/metrics/Metrics explained.md

Goal:

  • agree that the product is a specialist governance-control-room application
  • agree that ordinary staff cannot validate advanced workflows unaided
  • agree that role-based testing is the correct rollout model
  • agree that prepared examples are required for advanced validation

Success criterion:

Management stops asking ordinary staff to prove specialist governance logic through exploratory testing.

Phase 2 — Project Owner training

Audience:

  • Project Owner
  • implementation lead
  • system steward

Resources:

  • PROJECT_OWNER_ORIENTATION_AND_TESTING_BOUNDARIES.md
  • GOVERNANCE_ACTION_CONCEPT_PRIMER.md
  • TRAINING_MANUAL.md
  • all current page operating guides

Goal:

  • enable the Project Owner to explain the system
  • identify which users need which training
  • identify which tests require prepared fixtures
  • decide which pages are ready for trained-user walkthroughs

Success criterion:

The Project Owner can distinguish:

  • usability concern
  • training gap
  • valid empty state
  • missing fixture
  • actual defect

Phase 3 — Trained governance-user walkthrough

Audience:

  • governance users
  • HR/governance analysts
  • risk/compliance users where relevant
  • implementation team members responsible for action follow-up

Resources:

  • GOVERNANCE_ACTION_CONCEPT_PRIMER.md
  • TRAINING_MANUAL.md
  • relevant page operating guides

Goal:

  • teach selected-workspace navigation
  • teach evidence, recommendation, decision, pilot, KPI, lineage, and review concepts
  • walk through one complete operating loop:
  • diagnose → recommend → decide → execute → measure → review → learn

Success criterion:

Trained users can safely identify:

  • selected item/path
  • current workspace area
  • action consequence
  • missing-data meaning
  • whether an action requires more evidence or a fixture state

Phase 4 — Ordinary staff readability check

Audience:

  • ordinary staff
  • representative staff reviewers
  • non-specialist users

Resources:

  • brief orientation excerpt only
  • selected page or screenshot walkthrough

Goal:

  • test readability and confidence boundaries, not advanced governance logic

Ask ordinary staff:

  • Can you tell what this page is about?
  • Can you identify the selected item?
  • Can you tell whether the page is asking you to review, act, or inspect?
  • Can you identify when something is missing or unavailable?
  • Which terms are unfamiliar?

Do not ask ordinary staff to validate:

  • predecessor linkage
  • continuity correction
  • threshold version effects
  • scenario trigger states
  • detailed lineage completeness
  • structural decision conversion consequences

Success criterion:

Ordinary staff feedback is used to improve wording and orientation, not to invalidate specialist governance functionality they were not trained to test.

Phase 5 — Fixture-based closure testing

Audience:

  • developer
  • advanced tester
  • Project Owner

Resources:

  • training manual
  • page guides
  • prepared fixture/test data

Goal:

  • close rare or state-dependent validation items

Priority fixture tests:

  1. scenario trigger-state validation:
  • insufficient evidence
  • weakly evidenced / weak support
  • supportable under current evidence
  1. carry-forward predecessor recommendation path
  2. linked recommendation series update/remove/correction states
  3. threshold-rule version and reassessment interactions
  4. pilot mixed-signal outcome
  5. lineage broken/complete path comparison

Success criterion:

Each advanced path is classified as:

  • pass
  • minor issue
  • material defect
  • not exercised because fixture not available

Practical rollout rule

Use this rule when assigning training or testing:

> Do not ask a user to test a workflow whose prerequisites they have not been trained to recognize.

Examples:

  • Do not ask ordinary staff to test predecessor selection if they do not understand assessment cycles, recommendation series, and carry-forward.
  • Do not ask staff to test threshold versioning if they do not understand governance floors, alert floors, reassessment triggers, and rule versions.
  • Do not ask staff to test scenario effectiveness if they do not understand scenario pressure, execution evidence, and governance consequence.
  • Do not ask staff to test evidence relinking if they do not understand that evidence links change downstream interpretation.

Closure standard for Stage 6C training resources

Stage 6C training resources are sufficient for current closure when:

  • management has a clear complexity/value explanation
  • the Project Owner has role and testing-boundary guidance
  • users have a core concept primer
  • the main manual acts as a training hub
  • the four major Governance Action page guides match the current selected-workspace UI
  • advanced validation is separated from ordinary staff readability testing
  • remaining fixture-dependent tests are not treated as casual smoke-test failures

This standard is now substantially met.
