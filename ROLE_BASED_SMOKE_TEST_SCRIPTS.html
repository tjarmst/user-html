Role-Based Smoke-Test Scripts

WorkPlace Conditions Governance

Stage 6N

Purpose

These smoke-test scripts support rollout readiness.

They are intentionally role-specific because different users are qualified to test different things.

The critical rule is:

> Ordinary staff should not be asked to discover hidden prerequisite states or validate advanced governance logic by exploration.

This means ordinary staff can test whether pages are readable, navigable, and contextually clear. They should not be asked to validate scenario trigger logic, predecessor/carry-forward conditions, continuity correction, threshold-rule branching, or hidden fixture states.

---

How to use these scripts

Use these scripts as short guided checks, not as exhaustive QA.

Each tester should record:

  • tester role
  • date
  • app version or codebase package
  • page tested
  • pass / issue / not applicable
  • short note if something is unclear

Use this result scale:

ResultMeaning
PassThe tester could complete the check and the result was understandable.
Minor issueThe result worked but wording, layout, or signposting was unclear.
Material defectA visible action or result was wrong, unsafe, missing, or misleading.
Not applicableThe data or state needed for this check was not present.

Important:

> Not applicable is not failure.

Script 1 — Ordinary Staff Readability and Navigation Check

Tester role

Ordinary staff member or non-specialist user.

Purpose

Check whether the application is readable, navigable, and visibly contextual.

This script does not test governance correctness.

What ordinary staff should test

Ordinary staff may test:

  • page names are understandable
  • navigation labels are clear
  • the selected item is visible
  • the page explains what it is for
  • empty states are understandable
  • instructions are not intimidating or overly technical
  • obvious wording problems are identified

What ordinary staff must not test

Ordinary staff should not be asked to test:

  • scenario trigger-state correctness
  • predecessor / carry-forward eligibility
  • continuity correction
  • evidence relinking validity
  • KPI threshold-rule logic
  • governance-action routing logic
  • board-pack semantic completeness
  • whether hidden prerequisite data exists

Ordinary staff check

CheckPass / issue / not applicableNotes
I can tell what application I am using: WorkPlace Conditions Governance.
I can find the main navigation/sidebar.
Page names are understandable enough to know where I am.
When a page has a selected item, I can see what item is selected.
If no data is available, the page explains what is missing or what to do next.
I can tell which area/tab/workspace I am in.
I can identify confusing words or phrases.
I am not being asked to infer hidden technical states.

Ordinary staff stop rule

Stop the test if the tester is being asked to decide whether advanced governance logic is correct.

Record:

Stopped — this check requires trained governance or fixture validation.

Script 2 — Trained Governance User Workflow Check

Tester role

Trained governance user.

Purpose

Check whether the main governance workflows are reachable, understandable, and action-context safe.

This script assumes the user has learned the basic concepts:

  • recommendation
  • KPI/reassessment
  • lineage
  • pilot
  • evidence
  • learning state
  • governance action
  • scenario pressure

Pages to check

  • Recommendations
  • KPI Dashboard
  • Lineage View
  • Pilot Tracker
  • Governance Action Queue
  • Governance Execution Review
  • Scenario Effectiveness Review
  • Comparative Cycle Review
  • Governance Summary

Script 3 — Project Owner Governance-Fit Check

Tester role

Project Owner.

Purpose

Check whether the application supports the intended governance model.

The Project Owner is not testing every hidden branch. The Project Owner is checking whether workflows support the doctrine and whether validation is being classified responsibly.

Project Owner check

CheckPass / issue / not applicableNotes
The application supports governance of workplace conditions rather than merely presenting survey results.
Structural conditions remain primary over symbolic claims.
Flourishing is treated as a governing condition/constraint/enabler, not as a replacement for legitimate organizational purpose.
Pages distinguish evidence, contradiction, weak support, and supportable states where needed.
Action controls show selected-item context before writes.
Review pages provide refresh/freshness controls where cached summaries are used.
Missing fixture states are classified as not exercised, not treated as failure.
Residual risks are explicitly recorded.
Ordinary staff are not assigned hidden-state validation tasks.

---

Project Owner fixture-classification check

Use this when reviewing fixture validation.

Fixture questionAnswer
Can the exact state be named before testing?
Can the expected result be named before testing?
Can the required data be named before testing?
Is the tester role appropriate?
If data is missing, is it recorded as not exercised?
If UI result is wrong despite valid fixture data, is it recorded as material defect?

Closure rule for Stage 6N

Stage 6N can be closed when:

  • role-based smoke-test scripts exist;
  • ordinary staff checks are limited to readability/navigation/context;
  • trained governance checks cover the main workflows;
  • Project Owner checks cover governance fit and residual-risk discipline;
  • developer/fixture checks cover rare branches and controlled defect checks;
  • no ordinary staff script asks users to discover hidden prerequisite states or validate advanced governance logic by exploration.

This document meets those requirements.
