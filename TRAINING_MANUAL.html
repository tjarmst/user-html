WorkPlace Conditions Governance Training Manual

Purpose of this manual

This manual is the training hub for the WorkPlace Conditions Governance application.

It should not be read as a single-page quick-start guide. The system is a specialist governance-control-room application. It helps a governance team test whether organizational change is improving real working conditions over time and whether those changes remain connected to legitimate value creation, structural evidence, execution, measurement, review, and learning.

The application is not a casual self-service dashboard. Some pages can be read by ordinary staff after basic orientation, but advanced governance-action workflows require trained users, prepared data, and role-specific test scripts.

Use this manual to understand:

  • what the system is for
  • who should use which parts
  • what training sequence to follow
  • how the main pages fit together
  • which separate learning resources to read before using complex pages
  • what ordinary staff can reasonably test
  • what should be tested only by trained governance users or fixture-based validation

Management purpose of the system

WorkPlace Conditions Governance helps leaders:

  • understand;
  • test;
  • decide;
  • govern;
  • revise;
  • learn.

The system is not merely a dashboard, compliance checklist, reporting pack, or page sequence. It is a governance operating discipline that helps management connect evidence, judgment, action, review, and learning.

Six management-intention questions

The system helps management answer six core questions.

QuestionOne-line explanation
What is structurally happening in the organization?Identify the actual conditions, constraints, patterns, and structural pressures shaping work.
What are people experiencing?Understand human experience, dignity, trust, voice, workload, conflict, and contribution conditions.
Where do stated values, trust signals, or symbolic claims diverge from actual structural conditions?Compare values language, trust signals, and cultural claims with evidence of real working conditions.
Which recommendations should be preserved, reformed, replaced, watched, accepted, or deferred?Make disciplined recommendation-gating judgments rather than reactive status updates.
Are interventions producing measurable improvement through pilots and KPIs?Distinguish proposed or accepted change from demonstrated improvement.
What should governance approve, block, reopen, qualify, or escalate?Decide what is ready, unsafe, unresolved, conditional, or urgent enough for higher attention.

Proposed change versus demonstrated change

An accepted recommendation is not evidence of improvement.

Improvement requires execution feedback:

recommendation
→ structural decision
→ pilot
→ KPI
→ evidence
→ review
→ learning

Pilots and KPIs help distinguish proposed change from demonstrated change.

Role-boundary reminder

Ordinary staff should not be asked to discover hidden prerequisite states or validate advanced governance logic by exploration.

Missing fixture data is not a defect. Classify it as:

not exercised — fixture unavailable

Performance-integrity reminder

The system must distinguish:

  • presentational performance;
  • value-realising performance.

Guiding question:

Are we observing a persuasive performance of alignment, or evidence that the intended value is actually being realised?

Core management message

If management says the system is too complicated for ordinary staff to test properly, the correct response is:

> That concern is valid. The system is not designed as a casual reporting dashboard. It is a specialist governance-control-room application. It needs role-specific training, prepared examples, and a clear distinction between ordinary staff review, trained governance use, Project Owner validation, and developer or fixture-based testing.

Complexity does not by itself invalidate the system.

The important question is whether the complexity is purposeful and governed. In this system, complexity exists because the app preserves links among:

  • diagnosis
  • evidence
  • recommendations
  • decisions
  • pilots
  • KPIs
  • thresholds
  • lineage
  • scenarios
  • governance actions
  • review history
  • learning

Those links are the system's value. They prevent the organization from treating activity, rhetoric, or good intentions as proof that conditions have improved.

The operating loop

The simplest way to explain the system is:

diagnose → recommend → decide → execute → measure → review → learn

This loop should guide training, testing, and management explanation.

Diagnose

The organization records structural conditions, survey perceptions, evidence notes, and score patterns.

Recommend

The system helps generate and qualify recommendations based on diagnostic evidence, risk, contradictions, and governance significance.

Decide

Recommendations can be accepted, revised, linked across cycles, or converted into structural decisions.

Execute

Decisions can lead to pilots, actions, or governance responses.

Measure

KPIs, pilot metrics, threshold rules, and evidence notes test whether execution is producing meaningful change.

Review

Governance review pages compare cycles, qualify execution, surface contradictions, and prepare board-level interpretation.

Learn

The system tracks whether recommendations, decisions, pilots, and evidence lead to validated learning, contradiction, revision, or reopening.

Core doctrine

The application is built around two governing doctrines.

1. Structural primacy

Structural systems generate durable conditions of flourishing.

This means the system gives special weight to:

  • workload design
  • incentives
  • decision rights
  • capability pathways
  • technology use
  • governance routines
  • authority and accountability
  • evidence-backed execution

Symbolic claims matter, but they do not substitute for structural adequacy.

2. Mission–flourishing integrity

The organization exists to pursue a legitimate value-creating objective under constraint.

Human flourishing in the workplace does not replace that objective. It is:

  • a non-violable human constraint on legitimate value creation
  • an operational enabler of truthful coordination, responsible agency, learning, adaptability, and sustained contribution

The system should not drift into treating internal cohesion, sentiment, or symbolic reassurance as the final objective.

User roles and testing boundaries

The system should be tested by different roles in different ways.

Ordinary staff

Ordinary staff can reasonably test:

  • whether pages open
  • whether page labels are understandable
  • whether the selected item is visible
  • whether the page purpose is broadly clear
  • whether obvious empty states make sense
  • whether the page feels navigable after orientation

Ordinary staff should not be expected to validate:

  • predecessor/carry-forward eligibility
  • continuity correction logic
  • threshold-rule versioning effects
  • scenario trigger states
  • recommendation-series linkage
  • structural-decision conversion logic
  • evidence-relating consequences
  • lineage completeness across multiple cycles
  • exact calculation or classification edge cases

If ordinary staff cannot test those advanced paths without extensive explanation, that is expected. It means the test was assigned to the wrong role or lacked prepared fixtures.

Trained governance users

Trained governance users can test:

  • evidence interpretation
  • recommendation workflow updates
  • recommendation continuity
  • conversion to structural decision
  • pilot metrics and linked KPIs
  • evidence relinking
  • pilot outcome recomputation
  • lineage interpretation
  • governance action follow-up
  • review-history implications

They should receive the Project Owner orientation, concept primer, and relevant page guide before testing.

Project Owner / implementation lead

The Project Owner should test:

  • whether the system supports the intended governance model
  • whether pages preserve the operating loop
  • whether local context cues are sufficient for trained users
  • whether role boundaries are clear
  • whether training resources match current UI
  • whether management-facing value and complexity are correctly framed

Developer or fixture-based validation

Developer or fixture-based validation is required for:

  • scenario trigger-state branches
  • precise continuity predecessor eligibility
  • carry-forward series behavior
  • seeded partial-data combinations
  • edge-case threshold logic
  • all rare lineage or historical transition states

These should not be assigned to ordinary exploratory testers.

Recommended training setup

For training and validation, use a prepared demo or fixture dataset.

Typical local run sequence:

python .\scripts\test_data_builder.py
streamlit run .\main.py

Use the builder output as the reference dataset for training. It identifies organizations, cycles, users, metrics, recommendations, pilots, KPIs, governance actions, scenarios, and readiness states.

If a workflow cannot be tested because the necessary predecessor, series, pilot, KPI, or scenario state does not exist, record it as:

Not exercised — valid fixture not available

Do not record it as a UI failure unless a known valid fixture exists and the expected action is still missing.

The application is most useful when users understand it as a repeatable governance loop across assessment cycles.

Cycle 1 — Baseline diagnosis

Goal:

> Establish a structured picture of current conditions.

Use this cycle to answer:

  • What is structurally happening?
  • What are people experiencing?
  • Where do symbolic claims and structural realities diverge?
  • Which risks require governance attention?

How to read selected-workspace pages

The refactored Governance Action pages use a selected-item or selected-path model.

The common pattern is:

  1. readiness panel
  2. summary or attention strip
  3. worklist or primary table
  4. selected item/path context
  5. workspace navigation
  6. area-specific detail and actions
  7. supporting/audit detail

This means a page may show one selected recommendation, KPI, lineage path, or pilot at a time.

Before using a write action, confirm:

  • which item or path is selected
  • which workspace area is active
  • what the action will change
  • whether the page explains unavailable actions
  • whether the necessary evidence, predecessor, KPI, pilot, or scenario state exists

A write action should not be used if the selected item is unclear.

Empty states and unavailable actions

Empty states are not automatically defects.

A page may legitimately say that no items exist yet, no linked evidence exists, no predecessor is available, no lineage path exists, or no scenario-linked data exists.

Use this interpretation:

  • No active cycle
  • setup or assessment cycle selection is required
  • No recommendations
  • recommendation generation or upstream scoring may be required
  • No predecessor
  • a valid prior-cycle recommendation and series may not exist
  • No linked evidence
  • evidence may not yet have been created or relinked
  • No linked KPI
  • the pilot or decision may not yet be measured in the governance KPI layer
  • No lineage
  • the path from recommendation to decision, pilot, KPI, or evidence may be incomplete
  • No scenario overlay
  • scenario pressure may not yet be linked to execution evidence

If the user cannot tell why an action is unavailable, that may be a documentation or UI-context issue. If the required data does not exist, it is not automatically a defect.

Evidence discipline

Evidence notes are not decorative.

They qualify whether system outputs should be trusted.

Evidence can:

  • support a recommendation
  • qualify a KPI
  • challenge a pilot outcome
  • explain a contradiction
  • reveal incompleteness
  • justify reopening review
  • provide audit context

Evidence relinking is an audit-significant action. It should be performed only when the user understands which entity the evidence is being attached to and why.

Continuity discipline

Recommendation continuity is one of the most advanced concepts in the system.

It concerns whether a recommendation in one assessment cycle is:

  • new
  • continued from a prior cycle
  • revised
  • superseded
  • retired
  • fragmented
  • carried forward through a recommendation series

Key terms:

  • recommendation series
  • the cross-cycle identity of a continuing recommendation issue
  • predecessor recommendation
  • the prior-cycle recommendation from which the current recommendation continues
  • carry-forward
  • the current-cycle continuation of a prior recommendation issue
  • continuity correction
  • a trained-user correction to the cross-cycle linkage

Ordinary staff should not be asked to validate continuity logic through exploration.

Use prepared fixture data for predecessor/carry-forward testing.

Scenario discipline

Scenario-linked pages test whether external or future-facing pressures are being met by evidence-backed execution.

A scenario signal does not prove that mitigation has occurred.

A scenario-linked recommendation, pilot, KPI, or governance response must still show:

  • execution evidence
  • measurement evidence
  • learning state
  • lineage
  • governance interpretation

Scenario-trigger-state testing should use prepared data. It should not be treated as an ordinary staff smoke-test responsibility.

Board and governance review discipline

Governance review pages should not be read as simple score reports.

They combine:

  • structural scores
  • evidence confidence
  • trajectory
  • recommendation continuity
  • scenario pressure
  • challenge state
  • execution status
  • governance consequence
  • review history

Board-pack outputs should be interpreted as qualified governance summaries, not as automatic truth.

A board-ready statement should make clear:

  • what is known
  • what is uncertain
  • what is contradicted
  • what requires action
  • what requires monitoring
  • what needs further evidence

Safe testing sequence

Use this sequence for a trained validation session.

1. Confirm setup

  • organization selected
  • active assessment cycle selected
  • test/demo data loaded
  • relevant users present
  • page readiness panels pass

2. Walk Baseline Pages

Confirm that input and diagnostic pages open and show expected data.

3. Walk Governance Action Pages

For each page, confirm:

  • readiness appears first
  • summary/worklist appears
  • selected item or path is visible
  • workspace areas are understandable
  • write actions are anchored to selected context
  • empty states explain missing data

4. Walk Review Pages

Confirm that review pages synthesize rather than merely repeat data.

5. Validate only prepared advanced paths

Use prepared fixture data for:

  • continuity predecessor/carry-forward
  • threshold-version effects
  • scenario trigger states
  • contradiction and challenge states
  • partial lineage states
  • conversion to structural decision

Do not ask users to discover these states by trial and error.

Smoke-test classification

Use these classifications.

Pass

The page or area opens and the user can understand:

  • what they are looking at
  • what item/path is selected
  • what the area is for
  • what action is available
  • what missing data means

Minor issue

The page is usable but:

  • wording is unclear
  • context is too terse
  • supporting detail is poorly signposted
  • a trained user can proceed but an occasional user may hesitate

Material defect

A material defect exists when:

  • the page crashes
  • readiness is bypassed or buried
  • a write action lacks selected-item context
  • a write action appears to affect the wrong item
  • a required action is missing for a valid data state
  • an empty workspace is blank without explanation
  • an advanced action is available but its consequence is unclear

Not exercised

Use this when the valid test data state does not exist.

Examples:

  • no valid predecessor/carry-forward pair
  • no scenario branch for insufficient evidence
  • no pilot with mixed evidence
  • no KPI threshold-version comparison case

Do not convert "not exercised" into failure.

Completion standard for training readiness

The training resources are adequate when a Project Owner can explain:

  1. what the system is for
  2. why it is not a casual dashboard
  3. how the operating loop works
  4. which roles can test which parts
  5. which pages require trained governance users
  6. which tests require prepared data
  7. how evidence, recommendations, decisions, pilots, KPIs, lineage, scenarios, and learning fit together
  8. why complexity is being managed through training and role boundaries rather than hidden inside oversimplified UI labels

A trained governance user is ready when they can:

  1. identify the selected item/path on each Governance Action page
  2. explain the purpose of each workspace area
  3. distinguish activity from evidence of effectiveness
  4. distinguish status from learning state
  5. understand continuity and carry-forward at a practical level
  6. interpret empty states and unavailable actions
  7. avoid using advanced write actions without adequate context
