KPI Dashboard Page Operating Guide

Workplace Conditions Governance Application

Fiftysixth_pass Stage 6C.5 amendment

Purpose of this guide

This guide explains how to use the KPI Dashboard after the Governance Action Pages refactor.

The page is now a selected-workspace page. It is not a simple KPI reporting screen and it is not a generic performance dashboard. It helps trained governance users inspect whether measurable outcome evidence supports, qualifies, contradicts, or reopens earlier governance judgments.

The KPI Dashboard sits inside the system operating loop:

> diagnose -> recommend -> decide -> execute -> measure -> review -> learn

KPIs belong mainly to the measure and review parts of that loop. They help governance ask whether structural decisions and pilots are changing real conditions.

A KPI is evidence. It is not automatic proof. KPI interpretation depends on threshold rules, baseline/current/target values, linked pilots, linked decisions, linked recommendations, and supporting evidence notes.

In the Stage A / Stage B / Bridge framing, KPI Dashboard is mainly Stage B: Change reality intelligently. KPI progress helps test whether action is changing conditions. It can also feed Bridge interpretation through execution feedback, threshold stability, lineage completeness, and governance review.

Use KPI signals alongside user/metrics/Metrics explained.md and user/metrics/Comprehensive Metric Reference.md so users can distinguish Stage A diagnosis from Stage B outcome evidence.

Before using this guide

Users should first read:

  1. PROJECT_OWNER_ORIENTATION_AND_TESTING_BOUNDARIES.md

Those documents explain why this system requires training, what ordinary staff can reasonably test, and why advanced actions such as threshold-rule versioning and reassessment logging should be validated by trained users or with prepared test data.

This page guide assumes the user already understands these basic terms:

  • assessment cycle
  • KPI
  • pilot
  • evidence note
  • evidence relinking
  • threshold rule
  • threshold version
  • reassessment trigger
  • learning action
  • lineage
  • governance state

What the KPI Dashboard is for

Use the KPI Dashboard to:

  • create or update KPI records for the selected assessment cycle;
  • scan KPI outcome coverage and at-risk KPI status;
  • identify KPI reassessment triggers;
  • inspect one KPI's connection to a pilot, structural decision, recommendation, and evidence;
  • relink existing evidence to a selected KPI;
  • inspect threshold rules that interpret KPI governance state;
  • create new threshold rule versions when interpretation rules need to change;
  • review whether threshold changes alter KPI governance meaning.

The page is for governance interpretation of outcome evidence. It is not only a data-entry page.

What the KPI Dashboard is not for

The KPI Dashboard is not for:

  • proving that a recommendation or pilot succeeded by KPI value alone;
  • casual staff testing of threshold-rule versioning without training;
  • full continuity, predecessor, or recommendation-series validation;
  • creating recommendations or structural decisions;
  • editing pilot outcomes directly;
  • replacing governance judgment with a numeric score;
  • changing thresholds without considering downstream interpretation.

Do not treat a positive KPI as conclusive unless lineage, evidence, threshold interpretation, and governance context support that reading.

The page pattern

The current page follows this pattern:

  1. Readiness panel
  2. KPI Summary and Alert Strip
  3. KPI workspace selector
  4. Workspace-specific content and actions

The KPI workspace selector contains:

  • KPI Outcomes
  • Reassessment
  • KPI Detail & Lineage
  • Threshold Rules

This pattern means users should not expect every KPI action to be visible at once. They should choose the workspace that matches the task.

The safe sequence is:

  1. Confirm the current organization and assessment cycle.
  2. Read the KPI Summary and Alert Strip.
  3. Choose the relevant KPI workspace.
  4. Confirm the selected KPI or threshold rule before using write actions.
  5. Read any local guidance before saving, relinking, logging reassessment, or creating a new threshold version.

Readiness and empty states

At the top of the page, the readiness panel checks whether required workspace context exists.

If no organization or assessment cycle is selected, the page should not proceed into KPI work.

If the selected cycle has no KPI items:

  • KPI Outcomes remains useful because users can create KPI records there;
  • Reassessment explains that KPI records must exist before reassessment triggers can be evaluated;
  • KPI Detail &amp; Lineage explains that KPI records must exist before detailed inspection is available;
  • Threshold Rules can still be available because threshold rules may be inspected or defaulted independently of KPI creation.

A sparse page is not automatically a defect. Ask:

  • Is an organization selected?
  • Is an assessment cycle selected?
  • Have any KPI records been created for this cycle?
  • Are there linked pilots if the user wants pilot-linked KPIs?
  • Are reassessment triggers expected for this data state?
  • Is the user in the correct workspace area?

KPI Summary and Alert Strip

The top summary strip shows:

  • KPIs tracked
  • Reassessment triggers
  • Governance alerts
  • At-risk KPIs

Use this strip as a first-screen orientation device.

It answers:

  • Does this cycle have measurable outcome coverage?
  • Are any KPI records creating governance attention?
  • Are any KPI outcomes already at risk?
  • Is reassessment likely to be relevant?

Do not use the summary strip as final interpretation. It points to where review is needed.

KPI Outcomes workspace

Use KPI Outcomes when the user needs to create, update, or scan KPI records.

This area includes:

  • Create or update KPI expander;
  • KPI creation form;
  • KPI outcome table;
  • KPI current values and governance-state chart;
  • KPI governance alerts table when alerts exist.

The KPI form includes:

  • KPI name
  • Domain
  • Linked pilot
  • Baseline
  • Current
  • Target
  • Status
  • Note
  • Save KPI button

Status options are:

  • tracking
  • on_track
  • at_risk
  • achieved

Safe use

Before saving a KPI, confirm:

  • the KPI belongs to the current assessment cycle;
  • the name is specific enough to distinguish it from similar KPIs;
  • the domain is meaningful for later threshold-rule interpretation;
  • the linked pilot is correct or intentionally set to none;
  • baseline/current/target values are entered consistently;
  • the note explains what the value represents.

A KPI can still be useful without linked evidence, but it is weaker as governance evidence until its evidence and lineage are clear.

Staff testing boundary

Ordinary staff can usually test whether the form is understandable and whether a simple KPI can be saved in prepared demo data.

Trained governance users should test whether the KPI is being interpreted correctly in relation to thresholds, pilot lineage, and reassessment.

Reassessment workspace

Use Reassessment when KPI outcomes may require earlier judgments to be revisited.

This area is available only when KPI items exist. If no KPI outcomes are available, the page explains that KPI records must be added before reassessment triggers can be evaluated.

When triggers exist, this area shows:

  • reassessment trigger table;
  • KPI name;
  • domain;
  • baseline;
  • current value;
  • target;
  • learning state;
  • recommended action;
  • explanation;
  • Log reassessment required section;
  • Select KPI trigger selector;
  • explanation caption for the selected trigger;
  • Log reassessment required button.

The local page guidance also states that threshold rule detail remains in Threshold Rules. This separation matters: Reassessment is where users log the need to revisit judgment; Threshold Rules is where users inspect or administer the interpretation rules.

Safe use

Before clicking Log reassessment required, confirm:

  • which KPI trigger is selected;
  • why the trigger exists;
  • whether the current KPI value is missing, below target, worse than baseline, mixed, or target-met;
  • what recommendation, decision, pilot, or governance interpretation may need review;
  • whether this is a real reassessment need rather than a data-entry problem.

Logging reassessment records a learning action. It should not be used as a casual acknowledgement button.

Staff testing boundary

Ordinary staff should not be asked to prove all reassessment trigger states by exploration. Trigger states depend on prepared KPI data, learning states, and threshold interpretation.

A better smoke test asks ordinary staff only:

  • Can you see whether there are reassessment triggers?
  • Can you identify the selected trigger before the log button?
  • Is the page clear that reassessment is different from threshold administration?

KPI Detail & Lineage workspace

Use KPI Detail &amp; Lineage when the user needs to inspect one KPI's traceability.

This area is available only when KPI items exist. If no KPI outcomes are available, the page explains that KPI records must be added before detailed inspection is available.

This area includes:

  • Inspect KPI selector;
  • KPI name, progress score, and status;
  • KPI note;
  • domain rule governance state, governance floor, and alert floor;
  • linked pilot and pilot outcome;
  • linked structural decision and decision status;
  • linked recommendation and recommendation status;
  • linked evidence for the KPI;
  • Relink existing evidence to this KPI selector;
  • Apply KPI evidence relink button.

Safe use

Before applying an evidence relink, confirm:

  • the selected KPI is the correct KPI;
  • the linked pilot, decision, and recommendation context is understood;
  • the evidence note actually supports or explains this KPI;
  • the evidence is not being linked merely because it is available;
  • the relink will not misrepresent what the evidence shows.

Evidence relinking attaches an existing evidence note to the KPI. It does not create new evidence and it does not prove that the KPI is valid.

How to read missing lineage

If the selected KPI has no linked pilot, decision, recommendation, or evidence, that does not always mean the page is broken. It may mean:

  • the KPI was created without a pilot link;
  • the pilot has not been converted from a decision or recommendation;
  • evidence has not yet been linked;
  • the current cycle lacks the required upstream records.

Treat missing lineage as a governance question: is the KPI merely a standalone measure, or is it intended to evidence a specific action pathway?

Threshold Rules workspace

Use Threshold Rules when the user needs to inspect or version the rules that interpret KPI progress.

This area includes:

  • threshold rule selector;
  • current version caption;
  • threshold rule version form;
  • threshold version comparison;
  • KPI governance-state impact of threshold changes;
  • threshold version history table.

The rule form includes:

  • Governance floor;
  • Alert floor;
  • Score weight;
  • Effective start date;
  • Active checkbox;
  • Create new threshold rule version button.

What threshold rules mean

A threshold rule defines how KPI values are translated into governance interpretation.

For example:

  • a KPI may be treated as above governance floor;
  • a KPI may fall below alert floor;
  • a KPI may carry a particular score weight;
  • a threshold version may apply from a particular date.

Threshold rules matter because a KPI's governance state can change when the interpretation rule changes. A movement in governance state may reflect real performance change, rule change, or both.

Safe use

Before creating a new threshold rule version, confirm:

  • which threshold rule is selected;
  • the selected rule domain;
  • the current version number;
  • effective start and end dates;
  • governance floor;
  • alert floor;
  • score weight;
  • whether the rule should be active;
  • why a new rule version is justified.

Do not create threshold versions just to test the button unless using disposable test data. Threshold versioning changes how KPI evidence is interpreted.

Staff testing boundary

Threshold-rule versioning is an advanced governance-administration action. Ordinary staff should not be expected to validate threshold-version logic without training and prepared fixture data.

A staff-level smoke test can check:

  • Is the selected threshold rule visible before the form?
  • Are the current version and values visible?
  • Is the Threshold Rules workspace clearly separate from Reassessment?

A trained-user test can check:

  • whether version comparison is meaningful;
  • whether rule-impact rows appear where expected;
  • whether cross-cycle KPI interpretation is not being confused with rule change.

Governance meaning of KPI outcomes

KPI outcomes become governance-relevant when they:

  • validate a pilot or action direction;
  • contradict expected outcomes;
  • remain below target;
  • worsen relative to baseline;
  • lack current values;
  • trigger reassessment;
  • create governance alerts;
  • show threshold-rule instability;
  • lack evidence linkage;
  • lack lineage to a pilot, decision, or recommendation.

A KPI should be read together with:

  • pilot outcome;
  • decision status;
  • recommendation status;
  • threshold rule;
  • linked evidence;
  • assessment cycle;
  • governance review context.

Downstream impact

KPI Dashboard feeds downstream interpretation by giving execution work measurable outcome evidence.

It connects to:

  • Pilot Tracker, through linked pilot outcomes;
  • Lineage View, through recommendation-to-decision-to-pilot-to-KPI traceability;
  • Governance Execution Review, through KPI context, learning closure, and progression decisions;
  • Scenario Effectiveness Review, when scenario-linked entities need outcome evidence;
  • Comparative Cycle Review, through KPI-related score movement and threshold-rule stability;
  • Governance Summary, through KPI alerts, threshold comparisons, learning closure, and board-pack sections;
  • Evidence Notes, through evidence linked to KPI records.

The practical downstream question is whether KPI evidence strengthens, qualifies, contradicts, or reopens the governance interpretation.

Common mistakes

Avoid treating a KPI as proof without checking threshold rules.

Avoid treating an achieved KPI as unqualified success when evidence is missing, lineage is weak, or thresholds shifted.

Avoid linking a KPI to the wrong pilot.

Avoid ignoring at-risk KPIs when recommendations, decisions, or pilots are marked validated.

Avoid logging reassessment without reading the selected trigger explanation.

Avoid assuming a KPI has governance weight when it has no lineage or evidence support.

Avoid changing threshold rules without checking version comparison and governance-state impact.

Avoid asking ordinary staff to validate advanced threshold or reassessment behavior without prepared data and role-specific instructions.

Best-practice review pattern

Use this sequence for trained governance review:

  1. Select the intended assessment cycle.
  2. Read the KPI Summary and Alert Strip.
  3. Open KPI Outcomes to create, update, or scan KPI records.
  4. Review KPI governance alerts before assuming outcomes are healthy.
  5. Open Reassessment to see whether KPI outcomes trigger learning follow-up.
  6. Open KPI Detail &amp; Lineage to inspect one KPI's pilot, decision, recommendation, threshold rule, and evidence trail.
  7. Relink existing evidence only when the evidence note genuinely belongs to the selected KPI.
  8. Open Threshold Rules to inspect the rule version interpreting KPI governance state.
  9. Use threshold comparison before making cross-cycle KPI claims.
  10. Record uncertainty as a governance interpretation issue rather than forcing the KPI to prove more than it can prove.

Smoke-test guidance

Do not ask an untrained user to prove all KPI Dashboard data-flow states.

Ordinary staff smoke test

Ask ordinary staff to check:

  • Can they see the KPI Summary and Alert Strip?
  • Can they identify the four workspace areas?
  • Can they tell where KPI creation happens?
  • Can they tell where reassessment is logged?
  • Can they tell where one KPI's detail and evidence linkage is inspected?
  • Can they tell where threshold rules are administered?
  • Do write actions appear after enough context?

Trained governance-user smoke test

Ask trained governance users to check:

  • KPI creation and update path;
  • reassessment trigger interpretation;
  • evidence relinking to a selected KPI;
  • threshold rule version context;
  • rule-impact interpretation;
  • missing lineage and missing evidence states.

Developer or fixture-based validation

Use prepared data to validate:

  • all reassessment trigger branches;
  • threshold rule version comparison edge cases;
  • rule-impact changes across domains;
  • sparse-data behavior;
  • default-threshold behavior;
  • cross-cycle interpretation where thresholds changed.

Training exercise

Use a prepared demo cycle with at least one KPI linked to a pilot.

Ask the trainee to:

  1. Open KPI Dashboard.
  2. Read the summary strip.
  3. Open KPI Outcomes and identify one KPI.
  4. Open KPI Detail &amp; Lineage and inspect that KPI.
  5. State the KPI name, current value, target, status, governance state, linked pilot, linked decision, linked recommendation, and linked evidence.
  6. Open Threshold Rules and identify the rule version being used for the KPI's domain.
  7. Explain whether the KPI supports validation, triggers reassessment, needs evidence relinking, or requires threshold-rule caution.

Completion standard:

The user can explain both the KPI result and the rule, lineage, and evidence basis used to interpret it. The user does not treat the KPI value alone as proof.
