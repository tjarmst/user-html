Cross-Cycle Recommendation Linkage Design Specification

Purpose

Add first-class persisted cross-cycle recommendation linkage so Comparative Cycle Review can track the progress of the same governance recommendation across multiple assessment cycles.

The app already preserves strong within-cycle lineage:

Recommendation -> Structural Decision -> Pilot -> KPI -> Evidence / Review History / Governance Action

This specification adds the missing cross-cycle continuity layer:

Recommendation Series
  -> Cycle 1 recommendation
  -> Cycle 2 carried-forward or revised recommendation
  -> Cycle 3 challenged recommendation
  -> Cycle 4 revised, validated, contradicted, or superseded recommendation

The goal is to prevent user input from becoming fragmented across cycles and to make cycle-to-cycle progress review explicit, auditable, and governed.

Goals

  • Persist recommendation continuity across assessment cycles.
  • Let users explicitly carry forward, revise, supersede, merge, or split recommendations.
  • Allow Comparative Cycle Review to compare recommendation progress by stable series, not only aggregate counts.
  • Preserve downstream lineage for each cycle while also showing multi-cycle continuity.
  • Connect recommendation continuity to human validation challenge states.
  • Support governance reporting and board-pack export.

Non-Goals

  • Do not automatically assume two recommendations are the same because titles are similar.
  • Do not collapse all cycle-specific recommendations into one mutable record.
  • Do not remove the existing `Recommendation` table.
  • Do not force every recommendation into a series before it can be used.
  • Do not infer progress solely from learning states; continuity must be explicit.

Current State

Current `Recommendation` records are cycle-scoped:

recommendations.assessment_cycle_id

Downstream entities link to a specific recommendation:

  • `StructuralDecisionItem.linked_recommendation_id`
  • `Pilot.linked_recommendation_id`
  • `KPIItem.linked_recommendation_id`
  • `EvidenceNote.linked_recommendation_id`
  • `ConclusionChallenge.linked_recommendation_id`

Comparative Cycle Review currently compares cycle-level signals:

  • scorecard deltas
  • learning-state count movement
  • governance action count movement
  • review history throughput
  • KPI threshold stability
  • trajectory and technology alignment summaries

It does not yet persist stable recommendation identity across cycles.

Design Summary

Introduce two new first-class structures:

  1. `RecommendationSeries`
  • Represents the durable governance issue or recommendation thread across cycles.
  1. `RecommendationCycleLink`
  • Connects one cycle-specific `Recommendation` to a `RecommendationSeries`.
  • Stores continuity status, carry-forward status, reviewer notes, and predecessor/successor relationships.

This keeps each cycle's recommendation immutable enough for historical review, while allowing the app to show continuity across cycles.

Recommended `continuity_status` values:

  • `new`

  • `revised`
  • `split_from_prior`
  • `merged_from_prior`
  • `superseded`
  • `validated`
  • `contradicted`
  • `closed_no_action`

Uniqueness:

  • One recommendation can have only one `RecommendationCycleLink`.
  • A series can have at most one primary link per cycle unless split/merge behavior is explicitly enabled.

Recommended constraints:

unique(recommendation_id)
unique(series_id, assessment_cycle_id, recommendation_id)

Optional later constraint:

unique(series_id, assessment_cycle_id, primary_flag)

if a `primary_flag` is added for split/merge cases.

  • `priority`

Carry-Forward Behavior

When a recommendation is carried forward:

  1. User selects prior recommendation or series.
  2. Service creates a new `Recommendation` in the target cycle.
  3. New recommendation copies:
  • domain
  • category
  • title
  • rationale
  • priority
  • owner if still active
  1. New recommendation resets:
  • status to `proposed` or selected status
  • due date to null or selected due date
  • learning state to `untested` or `in_test`
  1. Service creates `RecommendationCycleLink`:
  • same `series_id`
  • target cycle
  • new recommendation id
  • `continuity_status = carried_forward` or `revised`
  • predecessor link or prior recommendation id
  1. Review History records both:
  • recommendation creation
  • series carry-forward

Review History Events

Use existing `ReviewHistory`.

Recommended events:

entity_type = "recommendation_series"
action_type = "series_create" | "series_status_update"

entity_type = "recommendation_cycle_link"
action_type = "recommendation_linked_to_series" | "recommendation_carried_forward" | "continuity_status_update"

Example:

recommendation_cycle_link #12:
recommendation_carried_forward
from Cycle 2 recommendation #8 to Cycle 3 recommendation #15

Fragmentation Detection

Add service method:

detect_recommendation_fragmentation(current_cycle_id: int) -> list[dict[str, object]]

Detection rules:

  1. Prior accepted or implemented recommendations without current-cycle link.
  2. Current recommendations with same normalized title/domain as prior recommendations but no shared series.
  3. Active series without current-cycle link.
  4. Series with challenged/unresolved human validation records but no revised recommendation in later cycle.
  5. Current recommendations linked to downstream decisions/pilots/KPIs but not linked to a series.

Each result should include:

  • severity
  • reason
  • prior recommendation id
  • current recommendation id
  • series id, if any
  • recommended action

Recommended severity:

  • `high`: accepted prior recommendation not carried forward
  • `medium`: similar unlinked recommendation found
  • `medium`: active series missing current cycle
  • `low`: proposed recommendation unlinked

Interaction With Human Validation Challenge States

The new `ConclusionChallenge` records can link to a recommendation.

With recommendation series added, governance review should be able to answer:

  • Was a challenged recommendation revised in the next cycle?
  • Did an unresolved conclusion get carried forward as an explicit open issue?
  • Was a revised-after-challenge conclusion connected to a revised recommendation?
  • Did a corroborated conclusion lead to validation or closure of a recommendation series?

Optional later model extension:

Add to `ConclusionChallenge`:

linked_recommendation_series_id: int | None
linked_recommendation_cycle_link_id: int | None

Recommended first pass:

  • Link challenge records to cycle-specific recommendations as already implemented.
  • Let `RecommendationSeriesService` infer series linkage through `RecommendationCycleLink`.

  • Nothing required for MVP continuity once this pass is complete.
  • Future enhancements can include split/merge UI, similarity suggestions, and graph visualization.

Migration Approach

This app uses SQLAlchemy `create_all()` plus SQLite-safe migration helpers.

First-pass migration should be additive:

  • new `recommendation_series` table
  • new `recommendation_cycle_links` table
  • no destructive changes to `recommendations`

Existing SQLite databases should continue to open. New tables should be created by `Base.metadata.create_all(bind=engine)` after the models are imported.

Recommended First-Pass Scope

Keep first implementation narrow:

  • one series per recommendation thread
  • one link per recommendation
  • carry forward from previous cycle
  • revise from previous cycle
  • detect missing continuity
  • show continuity in Comparative Cycle Review and Governance Summary

Defer:

  • true split/merge UI
  • advanced similarity matching
  • bulk reconciliation wizard
  • graph visualization
  • series-level ownership workflows beyond simple owner field

Why This Prevents Fragmentation

Without this feature, users can recreate similar recommendations in each cycle and the app can only compare aggregate movement.

With this feature:

  • the same governance issue has a stable `RecommendationSeries`
  • each cycle keeps its own historical recommendation record
  • carry-forward and revision are explicit user actions
  • downstream decisions, pilots, KPIs, evidence, and challenge records remain cycle-specific
  • Comparative Cycle Review can compare progress across the same recommendation thread
  • Governance Summary can flag unlinked or dropped recommendations before they disappear from institutional memory
