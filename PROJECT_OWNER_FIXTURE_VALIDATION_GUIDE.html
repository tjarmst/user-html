Project Owner Fixture Validation Guide

Explanation:

A fixture means the prepared conditions a test needs in order to run predictably.

That usually includes one or more of:

specific test data

database records

files

objects created before the test

mocked services or API responses

configuration values

initial application state

setup and cleanup steps

So a test fixture is not the test itself. It is the known setup that lets the test exercise a specific behavior and know what result to expect.

Purpose

This guide helps the Project Owner turn advanced validation questions into prepared fixture tests.

It exists because some parts of the Workplace Conditions Governance platform are too conceptually and data-flow dependent for ordinary staff to validate by exploration.

The goal is to prevent this situation:

> A staff member is asked to click around until they discover whether a complex state exists, without knowing the required predecessor data, expected result, or governance meaning.

Instead, the Project Owner should define:

  1. the fixture state,
  2. the prerequisite data,
  3. the expected UI result,
  4. the role allowed to test it,
  5. the pass/fail/not-exercised rule.

This turns advanced testing from exploratory confusion into controlled validation.

Core rule

Use this rule for all advanced validation:

> If the expected prerequisite data cannot be named in advance, the test is not ready for ordinary staff or general smoke testing.

For example, do not ask an ordinary user to test carry-forward if nobody can name:

  • the prior-cycle recommendation,
  • the current-cycle recommendation,
  • the recommendation series,
  • the expected predecessor,
  • the expected continuity state.

If those are unknown, the correct classification is:

Not ready for user testing — fixture not defined.

Difference between smoke testing and fixture validation

Smoke testing

Smoke testing asks:

  • does the page open?
  • is the selected item visible?
  • are labels understandable?
  • is an obvious empty state explained?
  • does a basic action appear in the expected area?

Smoke testing is suitable for ordinary staff only when the task is simple and visible.

Fixture validation

Fixture validation asks:

  • does the system render the correct state when a known data condition exists?
  • does a specific predecessor appear?
  • does a scenario branch classify correctly?
  • does a threshold-version case behave as expected?
  • does lineage show a complete or broken path as designed?

Fixture validation is not ordinary exploration. It requires prepared data and expected outcomes.

User-role boundary

RoleSuitable validation
Ordinary staffreadability, navigation, selected-item visibility, obvious empty states
Trained governance userevidence, recommendation, KPI, pilot, lineage, and learning workflows where data is prepared
Project Ownerdefine validation questions, approve expected outcomes, classify not-exercised states
Developer / fixture testercreate or confirm data states, inspect database/export evidence, validate rare branches

Ordinary staff should not be asked to discover hidden prerequisite states.

Metric-role fixture prompts

Some validation cases should now explicitly test whether users can distinguish Stage A, Stage B, and Bridge signals.

Use these fixture prompts when validating score-heavy workflows:

Fixture questionRequired prepared stateExpected user interpretation
Can the user identify a Stage A diagnostic signal?A scorecard with visible structural_health_index or symbolic_legitimacy_index.The user says this diagnoses current reality, not proof that change worked.
Can the user identify a Stage B execution signal?A pilot or KPI with outcome/progress evidence.The user says this tests whether action is working.
Can the user identify a Bridge signal?An integrity gap, lineage drop-off, scenario pressure, contradiction, or confidence qualifier.The user says this qualifies governance interpretation.
Can the user avoid overclaiming?A positive score with weak evidence or missing lineage.The user qualifies the claim rather than treating the number as assurance.

If the required scorecard, pilot, KPI, lineage, or evidence state is not prepared, classify the case as:

Not exercised - metric-role fixture unavailable.

Fixture-test classification

Use only these classifications.

Pass

Use when:

  • the required fixture data exists,
  • the expected UI state is visible,
  • the result matches the expected outcome.

Example:

Expected: predecessor recommendation appears.
Actual: predecessor recommendation appears.
Classification: Pass.

Minor issue

Use when:

  • the expected state appears,
  • the workflow is usable,
  • but wording or signposting could be clearer.

Example:

Expected: continuity warning appears.
Actual: warning appears, but wording may be too terse.
Classification: Minor issue.

Material defect

Use when:

  • the required fixture data exists,
  • the expected UI state should appear,
  • but the UI gives the wrong result, hides the action, or allows an unsafe action.

Example:

Expected: carry-forward requires predecessor.
Actual: UI allows carried-forward save without predecessor.
Classification: Material defect.

Not exercised

Use when:

  • the required fixture data does not exist,
  • the tester cannot name the required prerequisite state,
  • the current demo data does not contain the branch.

Example:

Expected: weakly evidenced scenario branch.
Actual: no known demo scenario produces this state.
Classification: Not exercised — fixture unavailable.

Do not convert not exercised into failure.

Fixture class 1 — Scenario trigger-state validation

Purpose

Scenario trigger-state validation checks whether the Scenario Effectiveness Review can distinguish different levels of scenario support.

In this guide, a fixture means a prepared, known test setup used to exercise a specific expected state. A scenario trigger-state fixture is not the validation itself; it is the scenario, recommendation, decision, pilot, KPI, evidence, and execution context that should cause the Scenario Effectiveness Review to display one expected result.

An execution fixture state means the prepared execution-side condition of that fixture: for example, whether a scenario-linked item has no downstream evidence, only partial decision support, or enough linked pilot/KPI/evidence support to make the mitigation claim supportable. Fixture requirements are the data elements that must exist before the state can be tested reliably.

The remaining target states are:

insufficient evidence
weakly evidenced / weak support
supportable under current evidence

These should not be discovered by ordinary staff clicking through the app.

They require known scenario/evidence/execution fixture states.

Scenario fixture requirements

For each scenario fixture, define:

  • scenario label or scenario pressure,
  • relevant domain,
  • linked recommendation, if any,
  • linked structural decision, if any,
  • linked pilot, if any,
  • linked KPI, if any,
  • linked evidence note, if any,
  • expected scenario-effectiveness state.

Scenario validation decision rule

Use this rule:

If the existing seeded/demo data produces all three states, validate them directly.
If one or more states cannot be located, create fixture requirements and mark those branches not exercised.

Do not ask ordinary staff to find these states by trial and error.

Fixture class 2 — Carry-forward / predecessor validation

Purpose

Carry-forward validation checks whether a current-cycle recommendation can be connected to a prior-cycle recommendation through a recommendation series.

This is one of the most advanced workflows in the system.

It requires known cross-cycle data.

Carry-forward requires

A valid carry-forward fixture needs:

  1. a prior assessment cycle,
  2. a current assessment cycle,
  3. a prior-cycle recommendation,
  4. a current-cycle recommendation continuing the same issue,
  5. a recommendation series,
  6. an expected predecessor recommendation,
  7. an expected continuity state.

If these cannot be named, the test is not ready.

Fixture class 3 — Threshold-rule / reassessment validation

Purpose

Threshold validation checks whether KPI threshold rules and reassessment triggers behave as expected.

This is not ordinary KPI reading. It is trained-user or fixture validation.

Threshold fixture requirements

Define:

  • KPI,
  • domain,
  • current KPI value,
  • applicable threshold rule,
  • threshold version,
  • governance floor,

Do not ask ordinary staff to validate threshold-version logic.

They can check whether the threshold rule area is readable. They should not be expected to prove rule-version effects.

Fixture class 4 — Pilot mixed-signal validation

Purpose

Pilot mixed-signal validation checks whether the system can interpret pilots that have both improvement and deterioration signals.

This prevents simplistic pilot-success interpretation.

How to use exports as fixture evidence

Exports are useful because they help identify candidate fixture rows before opening the UI.

For each uploaded/exported CSV, the Project Owner should ask:

  1. What cycle is this?
  2. What entity type is exported?
  3. Which row looks like the candidate fixture?
  4. Does it contain enough fields to prove the prerequisite state?
  5. What additional data is needed from the UI or database?

Example:

A recommendation export can show title, domain, cycle, continuity, evidence count, decision count, and scenario label.

It may support continuity fixture planning.

It usually cannot by itself prove scenario-effectiveness state, because scenario validation may also depend on linked pilot, KPI, lineage, and evidence data outside the recommendation export.

How to avoid Project Owner overload

Use this three-question shortcut.

Before testing an advanced state, ask:

1. Can I name the exact row/entity we are testing?
2. Can I name the expected UI result?
3. Can I name the data required for the result to appear?

If the answer to any question is no, do not test yet.

Record:

Fixture not defined — not ready for validation.

This is a fixture test. It should not be assigned to ordinary staff.

Example: scenario trigger-state validation

Fixture not yet ready

If the Project Owner can say only:

that is not yet a scenario fixture.

A valid scenario fixture must say:

This scenario pressure has this recommendation, this decision, this pilot, this KPI, and this evidence pattern, and therefore should display weak support.

If that cannot be said, record:

Scenario fixture not defined — data insufficient.

Use this workflow for every remaining advanced branch.

Step 1 — State the branch

Example:

Scenario Effectiveness Review should show weak support.

Step 2 — Name the fixture

Example:

Scenario fixture S2 — AI governance recommendation with decision but no pilot/KPI/evidence closure.

Step 3 — Name the required data

Example:

scenario_high technology recommendation
linked decision exists
no linked pilot evidence
no linked KPI evidence

Step 4 — Predict the UI result

Example:

If the expected result cannot be predicted, the fixture is not ready.

Step 5 — Assign the tester

Example:

Project Owner or trained governance user.
Not ordinary staff.

Step 6 — Test and classify

Use only:

  • Pass
  • Minor issue
  • Material defect
  • Not exercised

When to create a developer fixture

Create a developer fixture when:

  • the state is rare,
  • the state is important for closure,
  • seeded data does not contain it,
  • ordinary users cannot reasonably construct it,
  • the expected result is clear enough to test.

Examples:

  • weak support scenario branch,
  • supportable scenario branch,
  • valid predecessor/carry-forward pair,
  • threshold-version edge case,
  • pilot mixed-signal outcome,
  • broken lineage path.

What to tell management

Use this statement:

> We are no longer asking staff to discover complex hidden data states by exploration. We are converting advanced validation into fixture-based tests. Ordinary staff will test readability and navigation. Trained governance users will test prepared workflows. Developer or fixture-based validation will test rare scenario, predecessor, threshold, pilot, and lineage branches.

This is the correct response to the concern that the system is too complicated for staff to test properly.

Completion standard

The Project Owner is ready to proceed when they can:

  1. distinguish smoke testing from fixture validation,
  2. name which role should perform each kind of test,
  3. classify missing data as not exercised rather than failure,
  4. define expected results before testing,
  5. avoid asking ordinary staff to discover hidden prerequisite states,
  6. identify when developer fixture creation is required.

The Project Owner does not need to memorize every system rule. They need to control the validation method.
