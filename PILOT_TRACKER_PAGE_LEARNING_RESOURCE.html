Pilot Tracker Page Operating Guide

Purpose

The Pilot Tracker page helps trained governance users turn structural decisions into tested learning.

It is not a generic project-status page. It is the place where the system asks:

> Did the pilot actually test the decision, produce evidence, connect to KPIs, and create learning that should affect future governance judgment?

The page sits in the operating loop:

diagnose → recommend → decide → execute → measure → review → learn

Pilot Tracker mainly covers the execute → measure → review → learn part of that loop.

In the Stage A / Stage B / Bridge framing, Pilot Tracker is primarily Stage B: Change reality intelligently. A pilot is execution evidence. It tests whether a recommendation or structural decision changes real conditions, and it can later inform execution_feedback_index, learning state, lineage review, and governance summary interpretation.

Pilot activity is not the same as pilot evidence. A pilot becomes valuable when its hypothesis, metrics, evidence notes, linked KPIs, and learning state show what was actually learned.

Use it to:

  • inspect pilots created from governed decisions
  • review the pilot outcome and learning state
  • record pilot learning actions
  • add or update pilot metrics
  • create linked KPI items
  • link evidence notes to a pilot
  • recompute pilot outcomes after meaningful measurement changes
  • inspect recommendation → decision → pilot lineage

The page is designed for trained governance users, Project Owners, or implementation leads. Ordinary staff may help confirm whether the page is readable, but they should not be expected to validate every metric, KPI, evidence, lineage, or outcome dependency without prepared training and seeded examples.

Why this page may feel complex

Pilot Tracker is complex because it does not merely ask whether a pilot happened.

It asks whether the pilot has become usable governance evidence.

That requires the user to understand several linked ideas:

  • the original recommendation
  • the structural decision made in response
  • the pilot created to test that decision
  • the pilot hypothesis
  • the metric evidence collected
  • the linked KPI pathway
  • the evidence notes that support, qualify, or contradict the numbers
  • the learning state created from that evidence
  • the downstream pages that will use the pilot outcome

A pilot can be active and still be weak from a governance perspective. A pilot can be completed and still be untested. A pilot can show improvement on one metric and deterioration on another. The page is designed to preserve those distinctions rather than collapse them into a simple success/failure status.

Current page model

The current Pilot Tracker page uses a selected-pilot workspace model.

The broad structure is:

  1. readiness panel
  2. pilot outcome summary
  3. pilot worklist
  4. selected pilot context
  5. selected workspace area
  6. area-specific action or supporting detail

The accepted workspace areas are:

Outcome | Metrics | Linked KPIs | Evidence | Lineage

The selected pilot context appears before the workspace areas. It is intended to anchor all later actions so that the user knows which pilot the action affects.

Typical selected-pilot context includes:

  • pilot title
  • outcome explanation
  • status
  • owner
  • scenario
  • learning state
  • outcome score

If the selected-pilot context is not visible before a write action, the action should be treated as unsafe or insufficiently anchored.

User roles and testing boundaries

Ordinary staff

Ordinary staff can reasonably test:

  • whether the page opens
  • whether the selected pilot is visible
  • whether labels are understandable
  • whether the page makes clear that pilot activity is not the same as pilot success
  • whether they can identify the selected pilot before reading workspace areas

Ordinary staff should not be expected to validate:

  • whether a pilot outcome calculation is correct
  • whether a linked KPI is the right governance KPI
  • whether lineage is complete across recommendation, decision, pilot, KPI, and evidence
  • whether evidence relinking is appropriate
  • whether a pilot should be scaled, redesigned, or stopped

Trained governance users

Trained governance users can test:

  • metric choice and metric values
  • linked KPI creation
  • evidence relinking
  • outcome recomputation
  • learning action selection
  • lineage interpretation
  • downstream implications for KPI Dashboard, Lineage View, Governance Execution Review, Scenario Effectiveness Review, Governance Summary, and Review History

Project Owner / implementation lead

The Project Owner should test whether the page:

  • supports the intended governance workflow
  • keeps selected-pilot context visible before actions
  • prevents pilot activity from being mistaken for evidence of success
  • explains why missing metrics, KPIs, evidence, or lineage matter
  • fits the broader training model for staff and governance users

Developer or fixture-based validation

Developer or fixture-based testing is required for:

  • precise outcome-calculation edge cases
  • seeded partial-data states
  • all downstream lineage combinations
  • scenario-linked pilot pathways
  • unusual missing-data or contradiction states

Pilot outcome summary

The top of the page summarizes the pilot outcome population.

It may show counts such as:

  • total pilots
  • validated
  • contradicted
  • in test
  • untested

Use this summary to understand the overall learning posture of the current cycle.

Do not treat the count of pilots as proof of progress. A cycle with many pilots may still have weak learning if most pilots are untested, inconclusive, or poorly linked to metrics and evidence.

Useful questions:

  • How many pilots exist?
  • How many have moved beyond activity into evidence-based learning?
  • Are there contradicted or inconclusive pilots requiring review?
  • Are most pilots still untested?
  • Does the summary suggest execution is outpacing measurement?

Pilot worklist and selected pilot

The pilot worklist lets the user select one pilot for detailed work.

Before using any workspace area, confirm:

  • which pilot is selected
  • what the pilot is trying to test
  • what status it is in
  • whether an outcome explanation is visible
  • whether the learning state is already known
  • whether the pilot has an owner or scenario context

The selected pilot is the anchor for the page. Metric entry, linked KPI creation, evidence relinking, outcome actions, and lineage review should all be interpreted as acting on or explaining this selected pilot.

If the user cannot identify the selected pilot before taking an action, the page should not be treated as safe for that action.

Outcome workspace

Use Outcome to review and act on the selected pilot's learning state.

The outcome area may show:

  • selected pilot summary
  • current outcome status
  • learning state
  • outcome score
  • outcome explanation
  • outcome action controls
  • learning note

What outcome means

Pilot outcome is not the same as pilot status.

  • Status says where the pilot is operationally: planned, active, paused, completed, cancelled, or similar.
  • Outcome says what has been learned from evidence.
  • Learning state says how the pilot should be interpreted for governance purposes.

A planned or active pilot may still be untested. A completed pilot may still be inconclusive. A pilot with one positive measure may still be contradicted if another measure deteriorates or evidence shows harm.

Common learning states

The page may classify pilots using states such as:

  • validated — the evidence supports the pilot's intended effect strongly enough to consider scaling or adoption
  • in test — there is some support, but not enough closure
  • inconclusive — signals are mixed or too weak for a firm conclusion
  • contradicted — evidence challenges the pilot hypothesis or shows deterioration
  • untested — there is not enough measurement evidence to interpret the pilot

How to review outcome safely

Before logging an outcome action, ask:

  • Does the selected pilot have meaningful metric evidence?
  • Are linked KPIs present where broader governance interpretation is needed?
  • Does evidence support, qualify, or contradict the metric result?
  • Is the outcome explanation consistent with the numbers and evidence?
  • Is the proposed action proportionate to the evidence?

Outcome actions should not be used as cosmetic labels. They create review-history records and influence later governance interpretation.

Metrics workspace

Use Metrics to record or review measures for the selected pilot.

Pilot metrics answer:

> What changed inside the pilot?

They should test the pilot hypothesis, not merely record that activity occurred.

A useful metric may include:

  • baseline value
  • current value
  • target value
  • notes explaining timing, limitations, or context

Choosing pilot metrics

Choose metrics that directly test the pilot claim.

Examples:

  • If the pilot aims to reduce workload strain, use workload, overtime, burnout, rework, or sustainability indicators.
  • If the pilot aims to improve capability pathways, use progression, contribution, skill-use, or retention indicators.
  • If the pilot aims to improve governance discipline, use decision quality, evidence completeness, review timeliness, or threshold adherence.
  • If the pilot aims to improve trust or participation, use participation quality, escalation quality, psychological safety, or confidence indicators.

Avoid metrics that are easy to collect but disconnected from the hypothesis.

Detached-form warning

Metric action controls should not appear as detached generic forms.

Before saving a metric, the user should be able to see or clearly infer:

  • selected pilot
  • why the metric belongs to that pilot
  • what the metric is intended to test
  • whether existing metric evidence already exists

If the metric form appears only as a generic set of fields without selected-pilot context nearby, treat that as a user-context problem.

Metric review discipline

Before recomputing an outcome, confirm:

  • the metric definition matches the hypothesis
  • the baseline is meaningful
  • the target is realistic and relevant
  • the current value is recent enough to interpret
  • notes explain measurement limitations
  • deterioration is not being hidden by one favourable metric

Do not recompute the outcome simply because the pilot status changed. Recompute when measurement evidence has materially changed or been corrected.

Linked KPIs workspace

Use Linked KPIs to connect the pilot to broader governance measurement.

Pilot metrics are local to the pilot. Linked KPIs make the pilot visible to the wider governance system.

Linked KPIs may later affect:

  • KPI Dashboard
  • Lineage View
  • Governance Execution Review
  • Scenario Effectiveness Review
  • Governance Summary
  • Review History

Why linked KPIs matter

A pilot can improve locally without proving a broader governance change. Linked KPIs help test whether the pilot matters beyond its immediate activity.

Use linked KPIs to ask:

  • Is the pilot creating measurable improvement?
  • Is the structural decision producing the intended outcome?
  • Should the recommendation be validated, revised, or reopened?
  • Has the pilot created movement that matters beyond the pilot team?
  • Does the KPI support threshold or reassessment interpretation?

Creating linked KPIs safely

Before saving a linked KPI, confirm:

  • the selected pilot is visible or clearly established
  • the KPI describes an outcome, not just activity
  • the domain matches the governance question
  • baseline, current, and target values are meaningful
  • the status reflects evidence, not optimism
  • the note explains interpretation limits

A poor linked KPI can make downstream governance interpretation look stronger than the evidence actually supports.

Evidence workspace

Use Evidence to attach existing evidence notes to the selected pilot.

Evidence relinking is audit-significant. It affects how downstream pages interpret the selected pilot.

Evidence helps explain whether pilot metrics should be:

  • trusted
  • qualified
  • challenged
  • treated as incomplete
  • treated as showing harm or contradiction

When to relink evidence

Use evidence relinking when an evidence note already exists and belongs with the selected pilot.

Before relinking, ask:

  • Is this note about the selected pilot?
  • Does it support, qualify, or contradict the pilot outcome?
  • Is the confidence level suitable for the conclusion being drawn?
  • Should the evidence also be linked to a KPI or recommendation?
  • Could relinking this note distort the interpretation of the pilot?

Evidence interpretation rules

Use these rules:

  • Supporting evidence can strengthen a positive pilot outcome.
  • Contradictory evidence can downgrade a favourable metric result.
  • Low-confidence evidence should qualify the conclusion.
  • Incomplete evidence should lead to monitoring or evidence strengthening.
  • Evidence of harm should trigger redesign or stop/review even if some metrics improved.

Do not ignore contradictory evidence because a KPI or metric looks favourable.

Lineage workspace

Use Lineage to inspect how the selected pilot connects back to the governance pathway.

The current Lineage area is designed to preserve selected-pilot focus while also showing broader cross-pilot lineage context.

It may show:

  • broader lineage summary metrics
  • compact cross-pilot lineage overview
  • selected-pilot lineage detail
  • recommendation → decision → pilot relationships
  • linked KPI and evidence state
  • drop-off points where execution or measurement is incomplete

What lineage proves and does not prove

Lineage proves that a pathway is visible.

It does not prove that the pathway worked.

A visible chain is useful because it shows whether a recommendation became a decision, whether the decision produced a pilot, whether the pilot has KPIs, and whether evidence exists. But the governance conclusion still depends on the quality of the metrics, KPI movement, evidence, and learning state.

How to interpret lineage

Ask:

  • Which recommendation created the pilot pathway?
  • Which structural decision is being tested?
  • Is the pilot attached to that decision?
  • Are KPIs attached to the pilot?
  • Is there evidence attached to the pilot?
  • Is there a learning outcome?
  • Is there a drop-off between decision, pilot, KPI, and evidence?
  • Does the broader lineage overview show other pilots with related gaps?

Lineage gaps are not merely administrative defects. They may indicate that the organization has acted without proving whether the action worked.

Recomputing pilot outcomes

The Recompute pilot outcome action updates the selected pilot's outcome interpretation from its metric evidence and logs a review-history event.

Use recomputation after:

  • adding a meaningful metric
  • correcting a metric value
  • adding enough measurement evidence to interpret the pilot
  • resolving an evidence issue that changes interpretation
  • reviewing whether the current outcome is stale

Avoid recomputing when:

  • no meaningful metrics exist
  • the pilot has only activity evidence
  • the selected metrics do not test the hypothesis
  • evidence is still contradictory or insufficient and no learning note explains the limitation

Recomputation does not make weak evidence strong. It only updates the system's interpretation from the evidence currently available.

Learning actions

Pilot learning actions record governance meaning.

Common learning actions may include:

  • scale candidate
  • redesign required
  • stop/review required
  • continue monitoring

Use learning actions when the pilot evidence justifies a governance posture.

Examples:

  • Use scale candidate only when metrics and evidence support the pilot strongly enough to consider expansion.
  • Use continue monitoring when there are early signals but not enough closure.
  • Use redesign required when the pilot shows a design weakness or does not test the intended hypothesis.
  • Use stop/review required when the pilot is contradicted, harmful, or no longer legitimate to continue as designed.

Learning actions are not ordinary status updates. They become part of the review history and can influence later governance interpretation.

Downstream impact

Pilot Tracker feeds several downstream surfaces:

  • KPI Dashboard uses linked KPIs to interpret threshold progress and reassessment triggers.
  • Lineage View uses pilots to trace recommendation → decision → pilot → KPI movement and expose drop-off.
  • Governance Execution Review uses pilot outcomes, KPI linkage, evidence, and scenario context to judge execution strength.
  • Scenario Effectiveness Review uses scenario-linked pilots to test whether mitigation claims have execution support.
  • Governance Summary uses pilot learning closure to surface validated pilots, contradicted pilots, and required review prompts.
  • Review History records pilot creation, recomputation events, evidence relinks, and learning actions.

A well-reviewed pilot can strengthen confidence in a structural decision. A contradicted pilot can reopen review. An untested pilot can show that execution happened without learning closure.

Empty states and partial data

Pilot Tracker must be interpreted carefully when data is missing.

No pilots

If no pilots exist, this usually means no structural decision has yet produced a pilot or pilot data has not been entered.

This is not necessarily a page error. It may be a workflow state.

Pilot exists but no metrics

The pilot may be operationally real but untested.

Do not treat the pilot as validated.

Pilot exists but no linked KPIs

The pilot may have local metric evidence but may not yet influence broader governance interpretation.

Pilot exists but no evidence

The pilot may have numbers but weak interpretive support.

Pilot exists but no lineage

The pilot may not be properly connected to the recommendation and structural decision path.

Mixed improvement and deterioration

The pilot should be treated as inconclusive or requiring careful review rather than forced into a success label.

What good use looks like

A strong Pilot Tracker workflow looks like this:

  1. A recommendation leads to a structural decision.
  2. The structural decision creates or justifies a pilot.
  3. The pilot has a clear hypothesis.
  4. The selected pilot is reviewed in Pilot Tracker.
  5. Metrics are chosen because they test the hypothesis.
  6. Linked KPIs connect the pilot to broader governance interpretation.
  7. Evidence notes are linked to support, qualify, or challenge the result.
  8. The pilot outcome is recomputed after meaningful data changes.
  9. A learning action is logged only when evidence justifies it.
  10. Downstream pages use the pilot's outcome, KPI movement, evidence, and lineage to qualify governance decisions.

This workflow helps the organization avoid symbolic execution. The pilot becomes a tested claim, not merely a reported activity.

Common mistakes

Avoid:

  • treating pilot launch as pilot success
  • treating pilot status as pilot outcome
  • choosing metrics because they are convenient rather than meaningful
  • creating KPIs that describe activity instead of outcome
  • ignoring contradictory evidence because one metric improved
  • relinking evidence without checking whether it belongs to the selected pilot
  • recomputing outcomes before metric evidence exists
  • scaling a pilot that is only in test or inconclusive
  • treating scenario linkage as mitigation evidence by itself
  • treating lineage visibility as proof of effectiveness
  • expecting ordinary staff to test advanced lineage and evidence states without training

Review questions for trained users

Use these questions when reviewing a selected pilot:

  1. What is this pilot trying to test?
  2. Which recommendation and structural decision does it come from?
  3. What is the current learning state?
  4. What metrics test the hypothesis?
  5. Are the baseline, current, and target values meaningful?
  6. Are linked KPIs present and appropriate?
  7. What evidence supports, qualifies, or contradicts the outcome?
  8. Is the outcome explanation consistent with the evidence?
  9. Has the pilot been recomputed after meaningful evidence changes?
  10. What learning action is justified?
  11. What downstream pages will be affected?
  12. Should the pilot scale, continue monitoring, be redesigned, stop, or reopen review?

Smoke-test guidance

For ordinary staff, smoke testing should be limited to:

  • page opens
  • pilot summary is visible
  • selected pilot is identifiable
  • workspace areas are understandable
  • obvious empty states are understandable

For trained governance users, smoke testing may include:

  • adding a pilot metric to a disposable/test pilot
  • creating a linked KPI
  • relinking an evidence note
  • recomputing the pilot outcome
  • recording a learning action
  • checking lineage context

For developers or fixture-based validation, smoke testing should include:

  • no-pilot state
  • pilot-without-metrics state
  • pilot-with-mixed-signals state
  • pilot-with-linked-KPI state
  • pilot-with-evidence state
  • pilot-with-complete lineage state
  • pilot-with-broken lineage state

Do not ask ordinary staff to infer hidden data prerequisites from exploratory testing.

Completion standard

A trained user understands this page when they can explain:

  • why a pilot is not automatically successful because it exists
  • how metrics test the pilot hypothesis
  • how linked KPIs carry pilot learning into broader governance interpretation
  • why evidence can support, qualify, or challenge pilot outcome
  • why recomputation should follow meaningful data changes
  • how learning actions affect review history
  • how lineage connects the pilot to recommendation and structural decision pathways
  • why untested, inconclusive, contradicted, and validated pilots require different governance responses
